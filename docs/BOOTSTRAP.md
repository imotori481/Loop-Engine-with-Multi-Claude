# BOOTSTRAP.md — ループエンジニアリングの設計思想

この方式が何を前提に動くかと、人間とプランナーが設計仕様書をどう書くかを述べる。
ランナーが強制する規則は `RUNNER_SPEC.md`、受け渡しの形は `AGENT_IO.md` にある。

---

## 0. 役割

人間が仕様書を書く。設計はプランナーが書き、人間が段ごとに承認する（`RUNNER_SPEC.md` §3）。

| 段 | プランナーが書くもの | 人間がすること |
|---|---|---|
| 上流 | 基本設計仕様書（`docs/basic/`） | 読んで承認するか、コメントを付けて書き直させる |
| 中段 | 詳細設計仕様書（`docs/modules/`）と受け入れ条件（`ac/`） | クリティックの指摘と合わせて読み、承認するか書き直させる |

プランナーはコードを書かない。実装は別プロセスで動く **ソルバー** が担当する。
**それが何であるかはプランナーの問題ではない**（Claude Code、Codex CLI、ローカルのモデルの
どれでも同じ設計が通る）。ソルバーは設計の全体を見られず、モジュールごとに記憶を失う。
したがって、各モジュールの詳細設計は「それ単体で読んで実装できる指示書」でなければならない。

---

## 1. この方式の設計思想（変更しないこと）

以下は、この方式が機能するための前提である。効率化のために崩さない。

### 1-1. 合格基準を書く者と、それを満たす者を分ける

受け入れ条件は**プランナーが書き、人間が承認する**。ソルバーはそれをテストコードに
翻訳するだけで、基準そのものは決められない。同じ主体が基準と実装の両方を持つと、
「テストが通った」は客観的事実ではなく自己申告になる。

### 1-2. Red を先に確認する

exit code 0 はテストが0件でも起きる。実装前にそのテストが**落ちること**を
確認して初めて、その後の green に意味が生まれる。

### 1-3. テストは実装フェーズ中は凍結する

AIは詰まるとテストを緩めにくる。テストファイルはハッシュで固定し、
書き換えを検知したら停止する。

### 1-4. リトライ上限は「失敗」ではなく「差し戻し」

上限に達したら、ランナーは止まった理由を `plan/FAILURE.md` に書き、中段に戻す。
人間はそれを読み、直す詳細設計を選ぶ。

- 実装の指示が足りない → そのモジュールの詳細設計の振る舞いを締める。受け入れ条件は変えない
- 受け入れ条件が悪い／到達不能 → そのモジュールの受け入れ条件を書き直す
- モジュールの分け方が悪い → 関わるモジュールをまとめて選び、契約から書き直す

設計が変わったモジュールは、緑でも流し直す。設計が変わらなかった緑のモジュールはそのまま残る。

**テストを通すために基準を緩めることは、いかなる場合もしない。**

### 1-5. コンテキストは contracts で受け渡す

後続のモジュールに渡すのは、依存先の**ソースコードではなく署名（契約）と振る舞いの説明だけ**。
これでモジュールが増えても1回あたりの入力量が一定に保たれる。
契約で表現できないモジュールは、分割の仕方が間違っているというシグナル。

### 1-6. 人間に聞くタイミングは事前に固定する

「迷ったら聞いて」はAIの主観に判断を委ねることになり、頻度が読めず、
結果として全部承認する習慣（警告疲れ）に落ちる。人間が判断するのは段の出口だけで、
下流の停止条件は客観的事実で決める（1-2 / 1-3 / 1-4）。

### 1-7. 権限を渡さない

隔離環境の中で、**sudo を持たないユーザー**で実行する。
モデルの意図を警戒するより、権限自体を渡さないほうが確実。詰まったとき
`sudo apt install` や `chmod 777` に手が伸びるのは、悪意ではなく最短経路の探索として
普通に起きる。

現在の隔離環境は WSL2 のディストロ（`RUNNER_SPEC.md` §1）。**WSL2 は既定では隔離されて
いない**（`/mnt/c` が見え、`.exe` が動く）ので、切ったうえで機械的に検証している
（§1-4）。「隔離環境を使っている」ではなく「隔離が今この瞬間効いている」が前提。

## 2. プロジェクトの前提

題材と要件は人間が仕様書に書き、`loop go` が `/srv/loop/human/in/spec/` に置く。
ここには**題材に依存しない前提だけ**を残す。

- **実行環境**: WSL2 `Ubuntu-24.04`。言語は Python、TypeScript、C++、C# のどれか。sudo なしユーザー（`solver`）
- **コードの置き場所**: 柵のコードのディレクトリ（既定 `src/`）の下のみ。テストは柵のテストの
  ディレクトリ（既定 `tests/`）の下のみ
- **モジュール**: 柵のコードのディレクトリの下の1ソースファイル（C++ は同じ名前のヘッダと実装の組）

### 意図的にループの外に置くもの

題材が変わっても、この線引きの引き方は変わらない。**「仕様通りに計算されているか」までが
テストの範囲で、「それが良いかどうか」は人が見て決める。**

- 検索エンジンなら、検索結果の「良さ」。スコアが仕様通り計算されているかまでがテスト
- インクリメンタルゲームなら、**バランスと手触り**。`cost(n)` が厳密に
  `base × 1.15ⁿ` であることは保証できるが、`1.15` が正しい数字かは保証できない。
  ゲームの価値のほぼ全部がそこにあるので、これは軽い話ではない

最終確認の段で人間が動かして確かめるのは、この部分だ。

## 3. 設計仕様書の書き方

形の規則は `RUNNER_SPEC.md` §6 にあり、ランナーが機械で確かめる。ここは中身の目安。

### 基本設計仕様書

短く。仕様書から取り出した要件、モジュールの分け方と各モジュールの責任、
**後から覆すと高くつく決定が1〜2個**、そして「v1でやらないこと」のリスト。

`## 概要` の節は全モジュールのソルバーに届く。具体的な値を書かない。値はモジュールの
詳細設計と競合する。

### 詳細設計仕様書

1. **1モジュール = 1ソースファイル**（C++ はヘッダと実装の組）。振る舞いを持たない型（データだけのクラス、列挙）は
   使うモジュールか、共有の型のモジュールに入れる
2. `## 振る舞い` には責任、規則、端での振る舞い、何のためにどのモジュールを使うかを書く。
   ソルバーが受け取る説明はこれだけなので、自己完結していること
3. `## 契約` は後続への唯一の受け渡し口。意味ではなく形を書く
4. 依存は循環させない。モジュールの順はランナーが依存から決める
5. **モジュールどうしをつなぐ統合の条件を置く**。単体テストが全部通っても継ぎ目は保証されない

### 受け入れ条件

1. 各モジュールに**正常系・境界値・異常系を最低1つずつ**。
   「別々の2人のエンジニアが同じテストを書ける」粒度まで具体的に
2. `then` は具体的な値を述べる。スタブが返しうる値（空、ゼロ、引数そのまま）を答えにしない
3. 依存先の実物と一緒に動かす条件は `kind` を `integration` にする。依存先の無いモジュールには置けない

## 4. 分割の目安

参考程度に。実際の粒度は仕様書で決める。

**良い題材の条件は「手計算した期待値と突き合わせられること」。** 受け入れ条件は
「別々の2人が同じテストを書ける」具体性が要るので、正解を手で出せる領域ほど書きやすい。

インクリメンタルゲームの核なら、こう割れる:

```text
データモデル（GeneratorType / GameState）
  ↓  class GameState(...)
コスト曲線
  ↓  generator_cost(gen_type, owned) -> float      base × growth ** owned
生産速度
  ↓  total_production_rate(config, state) -> float
時間経過
  ↓  advance_time(state, config, now) -> GameState
購入 / 一括購入
  ↓  buy_generator(state, config, gen_id) -> GameState
セーブ・ロード
  ↓  save_game(state, path) / load_game(path)
```

例:「given: base_cost=10.0, cost_growth=1.15, owned=5 / then: 20.113571875（絶対誤差 1e-6）」

**境界値と異常系が自然に出てくるのがこの題材の強み。** 経過時間0 / 負の経過時間
（時計の巻き戻り）/ 極端に長い放置 / 所持数0のコスト / 資金不足での購入 /
存在しない発電機 id / 巨大数の精度 / 空のセーブ / 壊れたセーブ。

なお `cost_growth ** owned` を含む値は二進丸めの影響を受けるので、
**手計算値との比較は絶対誤差付き**にすること（整数や単純な和積は厳密比較でよい）。
この使い分けは、そのモジュールの詳細設計の振る舞いに書く。

---

## 5. やらないこと

- コードを書く（実装はソルバーの担当）
- 受け入れ条件を曖昧なまま承認する
- モジュール数を減らすために1モジュールを太らせる
- 下流で止まったモジュールに対して基準を緩める形で応じる
- 「たぶんこうだろう」で仕様を埋める（仕様書に無い決定は基本設計に書き出し、人間の承認に委ねる）

# RUNNER_SPEC.md — ループランナー仕様

BOOTSTRAP.md の 1-2 / 1-3 / 1-4 / 1-5 および `files_write` 許可リストを、
**文章ではなく機構として**実装するためのプログラムの仕様。

対象読者は、このランナーを実装する人間（初版は手書きし、捨てる前提）。

---

## 0. 位置づけ

### 0-1. 役の配置

| 主体 | 実体 | 実行場所 | 権限 | 見えるもの |
|---|---|---|---|---|
| プランナー | **Claude Code** | サンドボックス / `planner` ユーザー | `/srv/loop/planner/out` への書き込みのみ | ランナーが組み立てたブリーフ（要件、計画、ESCALATION.md） |
| ランナー | **このプログラム**（AI ではない） | サンドボックス / `runner` ユーザー | リポジトリ全体の所有、git、sudo なし | tasks.json 全体、台帳、テスト結果 |
| ソルバー | **Claude Code**（ファイルの読み書きのみ。差し替え可。§4-4-1） | サンドボックス / `solver` ユーザー | 限定的な書き込みのみ。コマンドは実行できない | ランナーが組み立てた1ステップ分のブリーフだけ |
| クリティック | **Claude Code** | サンドボックス / `critic` ユーザー | `/srv/loop/critic/out` への書き込みのみ | 計画のブリーフだけ。計画の元ファイルもテストも読めない |

**AI でないのはランナーだけ**。ランナーは決まった手順を実行するだけなので、
プログラムで書く。判断を AI に委ねると「まあ通ったことにする」が起こり得るが、
関門の値打ちは**判断しないこと**にあるため。

AI の3役は別々の uid で動き、資格情報も `/etc/loop/<役>.env` に分かれている。
各ファイルはその役の uid だけが読める。ランナーは sudo を持たず、
`/etc/sudoers.d/` にある役ごとの起動スクリプトへの例外でだけ他の uid を起こす。

サンドボックスは WSL2 のディストロ（§1-1）。保守ユーザー（sudo あり）も同じ
ディストロにいるが、ループの役には含まれない。

**プランナーは plan/ を直接書けない。ソルバーは plan/ を読めない。**
この2つが崩れると以下の全部が意味を失う。どちらもファイルシステムの権限で決まる。

サンドボックスの外側は**規律であって機構ではない**。Windows からは `wsl -u root` で
いつでも中の root になれるので、境界は片方向にしか立っていない ── 守っているのは
「サンドボックスから Windows 側へ手が伸びない」方向だけである（§1-4）。
人間の作業環境はサンドボックスの中身に手を入れない。

### 0-2. 非目標

- ソルバーの実装（Claude Code 等をサブプロセスとして呼ぶだけ）
- LLM API の抽象化（1種類決め打ちでよい）
- 並列実行（ステップは全順序で1本ずつ）
- ディストロの作成・スナップショット操作（ホスト側の責務。§1-5）
- サンドボックスの生存管理（WSL2 はアイドルで落ちる。ホスト側 keepalive の責務。§1-6）

### 0-3. 設計原則

> **検知より剥奪。** ある関門を「違反を検知して止める」で実装できるときと
> 「そもそも実行不能にする」で実装できるときは、後者を選ぶ。
> 検知は二重化のためのトリップワイヤとしてのみ併置する。

BOOTSTRAP.md 1-7 の考え方を、テスト凍結と許可リストにも適用する。

## 1. 実行環境

### 1-1. サンドボックス

- **WSL2 ディストロ `Ubuntu-24.04`**（Ubuntu 24.04.1 LTS / `[boot] systemd=true`）
- `.wslconfig` で 6 プロセッサ / 8 GB RAM / swap 4 GB / `sparseVhd`
- リポジトリはディストロ内の **ext4 (VHDX) 上**。`/mnt/c` は使わない（理由は 1-4）
- `networkingMode=NAT`（**`mirrored` は使わない**。理由は 1-4）
  - 外部への egress（LLM API 用）
  - ホストからの SSH / git push/pull は、ディストロ内 sshd が **2222 で listen** し、
    `localhostForwarding=true` によって Windows の `127.0.0.1:2222` に出る

> VirtualBox から WSL2 に移した。ホストで Hyper-V が有効だと VirtualBox は NEM モードに
> 落ち、Linux ゲストが起動時に2回に1回ハングして数時間のループに使えなかった。
> 経緯と得失は `provision/README.md` §6。
>
> 「ソルバーが git 経路に触れられない」は**鍵を持たせないこと**で担保しており、
> ネットワーク構成には依存していない（`AllowUsers` にも載せない。§1-2）。

### 1-2. ユーザーとファイル所有

```
maint : uid 1000. ディストロの既定ユーザー。sudo あり。保守と VS Code の接続先。
          ループの実行主体ではない。
runner  : uid 1001. リポジトリ全体を所有。sudo なし。SSH 鍵あり。
solver  : uid 1002. sudo なし。SSH 鍵なし。sshd の AllowUsers に載せない。
          他ユーザーの $HOME 参照不可（`maint` の home も。ここに人間の鍵と
          エージェント CLI の認証情報が入るため）。
```

リポジトリは **`/srv/loop/` に置く。どの home にも置かない。**
`/home/runner/project` にすると、solver が project に降りるために `/home/runner` に
通過権限が必要になり、home を 700 にできなくなるため。

```
/srv/loop/
  repo.git/         bare。ホスト（プランナー）が push、runner が pull
  project/          ループが回る作業ツリー
  brief/            runner → solver の唯一の受け渡し口（§5）
```

`/srv/loop/project` 配下の権限（`X` = ステップ位相により変化）:

| パス | 所有 | モード | solver から |
|---|---|---|---|
| `project/`（ルート自体） | runner:solverw | **3775**（setgid + **スティッキー**） | 新規作成のみ。runner 所有物の削除・改名は**不可** |
| `.git/` | runner:runner | 700 | **不可**（読みも不要） |
| `plan/` (tasks.json, CONTEXT.md, ledger.jsonl) | runner:runner | 700 | **不可** |
| `.runner/` (凍結マニフェスト) | runner:runner | 700 | **不可**（何を照合しているか見せない） |
| `tests/` | runner:solverw | `X`: 2775 → **555** | TEST_WRITE 中のみ書、FREEZE 以降 読のみ |
| `src/` | runner:solverw | 2775 | 書（§4-4 の経路チェックあり） |
| `conftest.py`, `pytest.ini`, `pyproject.toml` | runner:runner | 644 | 読のみ（常時。**スティッキー依存** ── 下記） |
| `.venv/` | runner:runner | 755 | 読・実行のみ、**書不可** |
| `/srv/loop/brief/` | runner:solverw | 750 | 読のみ |

**ルートが書ける理由と、スティッキーが要る理由**（2026-08-18 実測）。Codex の
`apply_patch` はワークスペースのルートを経由して書くため、ルートが読み取り専用だと
`src/` に権限があっても全ての編集が失敗する（しかも失敗は対象ファイル名で報告され、
原因から遠い）。しかし**書けるだけでは穴になる** ── unlink と rename はファイルではなく
**親ディレクトリ**の書き込み権で決まるので、`conftest.py` を改変できない solver でも
削除して自作に差し替えられてしまう。テストの収集方法は FREEZE が守るべきものの中心なので、
これは凍結の実質的な無効化にあたる。スティッキービットは「削除・改名は所有者のみ」に
制限するのでこれを塞ぐ。solver は**新規作成だけできて runner の持ち物には触れない**。
`40-perms.sh` が両方を assert する（作れること／消せないこと）。

残る経路が1つある。solver はルートに**新規ファイルを置ける**ので、`AGENTS.md` のような
エージェントが自動で読む文書を仕込める。`--ignore-rules` で `.rules` は閉じているが
`AGENTS.md` は別。**ランナーはステップ開始前にルート直下のファイル一覧を許可リストと
照合すること**（`--ephemeral` はセッションの永続化を止めるだけで、ファイル経由の持ち越しは
止めない）。

CONTEXT.md も含め **solver は `plan/` に一切アクセスしない**。ソルバーが受け取るのは
runner が `brief/` に組み立てたその1ステップ分のブリーフだけ（§5）。
これで「tasks.json を覗く」経路が権限レベルで存在しなくなる。

ソルバーは `solver` グループ経由で `src/` にのみ書き込む。
テスト凍結（1-3）は **FREEZE 位相で `chown runner:runner tests/ && chmod -R a-w tests/`**
によって実装する。ハッシュ照合は二重化のトリップワイヤであって主機構ではない。

### 1-3. sudo を渡さない理由はサンドボックスでは変わる

隔離が効いていれば（§1-4）、仮にディストロ内で root を取られても Windows 側への
被害はほぼない。したがって `solver` を sudo なしにする目的は**安全性ではなく再現性**である。

`apt install` や `pip install` が通ってしまうと、CONTEXT.md に書かれた環境と
実際の環境が乖離し、green が再現不能になる。**環境の変更は必ずエスカレーションとして
表面化させる**（= 詰まったので勝手に入れた、を検出可能にする）ことが目的。

**ただし、この目的は egress を塞がなくても既に達成されている**（2026-08-18 実測、
ネットワーク全開の状態で）。

| 試みたこと | 結果 | 効いている機構 |
|---|---|---|
| `.venv/bin/pip install requests` | Permission denied | `.venv` が runner 所有・`go-w` |
| `pip install --user requests` | externally-managed-environment | PEP 668 |
| `--user` で入れたものを `.venv/bin/python` から import | 見えない | venv は user site を無視する |
| `apt-get install` | dpkg lock: are you root? | sudo なし |

3つ目が要になっている。**テストは必ず `.venv/bin/pytest` で走らせること** ── ここを
素の `python3` に変えると user site が復活し、この防御だけが崩れる。

したがって egress 制限が買うのは環境凍結ではなく、**外部からの持ち込みと持ち出し**
（ソルバーが web から指示や実装を拾う／プロジェクトを外に出す）である。優先度は
そちらの脅威をどう見るかで決まり、環境凍結の前提条件ではない。

以下は持ち込み・持ち出しを塞ぐ場合の構成:

```
# 既定 DROP、プロキシ経由のみ許可（uid ベース）
iptables -A OUTPUT -m owner --uid-owner solver -o lo -j ACCEPT
iptables -A OUTPUT -m owner --uid-owner solver -d <proxy> -p tcp --dport 3128 -j ACCEPT
iptables -A OUTPUT -m owner --uid-owner solver -j DROP
```

ローカルの許可ドメインのみ通すフォワードプロキシ（tinyproxy 等）を `runner` で動かし、
許可先は **LLM API のドメインのみ**。PyPI も apt も通らない。

> v1 簡易版: プロキシを立てず、`--uid-owner solver` で DNS(53) と API の IP のみ ACCEPT。
> IP 変動で壊れるので、壊れたら上の構成に上げる。
>
> **この簡易版は現状では勧められない**（2026-08-18 実測）。ソルバーの実際の宛先は
> `chatgpt.com` の1つだけだが、それは Cloudflare の後ろにあり、いま2アドレスに解決される。
> IP 固定は黙って陳腐化する。しかも WSL2 では VM が頻繁に止まるので規則の永続化が要り、
> **永続化した固定 IP は時限爆弾になる**（ローテーション後、原因の分かりにくい停止として出る）。
> 塞ぐならプロキシ構成で作ること。
> WSL2 のイメージには iptables が入っていないので `60-egress.sh` が自分で入れる。
> また VM がアイドルで落ちるたびにルールが消えるため、`iptables-persistent` は必須。

### 1-4. 隔離は既定では成立していない

WSL2 は VirtualBox と違い、**既定でホストと地続き**である。3つを明示的に切って初めて
サンドボックスになる。

| 既定の挙動 | 切り方 | 切らないと |
|---|---|---|
| Windows ドライブを `/mnt` にマウント | `/etc/wsl.conf` `[automount] enabled=false` | solver が Windows のファイルを読み書きできる |
| `.exe` を起動できる（interop） | `[interop] enabled=false` + `appendWindowsPath=false` | solver が `powershell.exe` を呼べる |
| WSLg（GUI/音声/クリップボード） | `.wslconfig` `guiApplications=false` | `/mnt/wslg` の誰でも読めるソケット経由で Windows 側のコンポジタと PulseAudio に届く |
| `mirrored` なら Windows の localhost に到達 | `.wslconfig` `networkingMode=NAT` | Windows 側で listen しているサービスに触れる |

これらは **root に対する防御ではない**。ディストロ内の root は
`mount -t drvfs C: /somewhere` でいつでも Windows ドライブを持ち込める（実測）。
効いているのは「`solver` は sudo を持たないのでマウントできない」という一点で、
つまり隔離の実質は §1-2 の権限モデルと同じ土台に乗っている。
interop の binfmt ハンドラも `enabled=false` でも登録されたまま残るので、
**ハンドラの有無は証拠にならない**（`provision/README.md` §3-9）。

`/mnt/c` を使わない理由はもう一つある。DrvFs は所有者とモードビットを正しく持てないため、
**`tests/` を solver から書き込み不可にする（1-2 の主機構）が成立しない。**
リポジトリはディストロのネイティブ ext4 上に置く。

これらは「設定を書いた」では確認にならない。`/etc/wsl.conf` と `.wslconfig` の変更は
`wsl --terminate` では反映されず `wsl --shutdown` が必要で、書いたまま効いていない状態が
普通に起きる。だから `provision/05-isolation.sh` が**現在の状態**に対して assert する
（マウントテーブル、`/mnt/c` の中身、PATH、`/mnt/wslg` の有無、systemd、`loopback0`）。

ホストとの受け渡しは git 経由（§2）。ホストから編集する場合は VS Code Remote-SSH で
`maint` に繋ぐ（`loop-dev` コマンド）。ファイルを送り込むときは `/mnt/c` が無いので scp。

### 1-5. スナップショットと git の役割分担

| 壊れたもの | 戻し方 |
|---|---|
| コード（green ステップを捨てる = 1-4(c)） | **git**。ステップ単位のコミットとタグ |
| 環境（何かが入った・壊れた） | **`wsl --export` / `--import`**。ホスト側から |

ランナーはスナップショットを操作しない。
プロビジョニング直後に `wsl --export` を1本取っておくこと。

VBox スナップショットに比べて差分が取れず数 GB になるので、頻繁には取れない。
危険な無人実行の前に1本、が現実的な運用。`--export` は停止状態が必要なので
`wsl --shutdown` を伴い、**その後 keepalive タスクの再起動が必要**（§1-6）。

### 1-6. サンドボックスの寿命 ── 無人実行はできない

WSL2 の VM は **約60秒アイドルすると VM ごと停止する**。しかもアイドル判定は
`wsl.exe` クライアントセッションだけを数え、**SSH のトラフィックは数えない**。
つまり VS Code Remote-SSH で接続中でも、デタッチしたループを走らせていても落ちる。
`vmIdleTimeout` は効かない（実測済み）。

これを抑えているのはホスト側の keepalive スケジュールタスクだけで、それは
ログオンセッションに紐づく。したがって:

- **ログオフを跨いでループを回すことはできない。** `runner run --all` は人が
  ログオンしている間だけ走る
- 途中で VM が落ちる可能性が常にあるので、**台帳（§6-1）からの再開が飾りではなく
  必須機能になる**。位相の途中で死んだ場合に安全側（当該ステップをやり直す）に
  倒れること
- 無人で数時間回す必要が出たら Hyper-V に移す。ディストロ内の構成はそのまま移せる

詳細は `provision/README.md` §3-1 と §5。

## 2. ホストとの境界

```
ホスト (Windows)                    WSL2 / Ubuntu-24.04
─────────────────                   ───────────────────
プランナー(Claude Code)
  └ plan/ を編集
     ↓
  作業クローン  ──push──▶  /srv/loop/repo.git (bare, runner 所有)
                ssh 127.0.0.1:2222 (runner)
                                    │
                                    │ runner が pull
                                    ▼
                          /srv/loop/project ──── ランナー & ソルバー
                                    │
  作業クローン  ◀──pull──────────────┘  (green コミット、ledger、ESCALATION.md)
```

- bare リポジトリはディストロ内に置き、ホストからは SSH で push/pull（`runner` 鍵）
- **`solver` は SSH 鍵を持たず、`AllowUsers` にも載っていないので、この経路に触れられない**
- `runner` 鍵は保守用（`maint`）の鍵とは別に作る。前者は git 経路専用
- プランナーが書き込んでよいのは `plan/SYSTEM_SPEC.md` / `plan/CONTEXT.md` / `plan/tasks.json` のみ。
  当初はこれを「pull 時に差分を検出したら停止する」検知として書いていたが、
  **検知ではなく剥奪で実装した**（§6-5）。プランナーは `plan/` にそもそも書けず、
  提案を `/srv/loop/planner/out` に置くだけで、そこに置ける名前は3つしかない

## 3. ステップのライフサイクル

1ステップは以下の位相を持つ。位相は `plan/ledger.jsonl` に記録され、中断しても再開できる。

```
 PLAN_LOAD
     │  tasks.json 検証・依存解決・ブリーフ組み立て
     ▼
 TEST_WRITE            ソルバー呼び出し #1（テストのみ書かせる）
     │                 書込許可: files_test のみ
     ▼
 STUB                  ソルバー呼び出し #2（スタブのみ書かせる）
     │                 書込許可: files_write のみ
     │                 指示: 「契約通りのシグネチャで、意図的に誤った値を返す」
     ▼
 RED_GATE ────────────▶ 不合格 → ESCALATE
     │  §4-1
     ▼
 REVIEW_GATE           人間がテストコードだけを1回見る（設定で無効化可）
     │  §4-2
     ▼
 FREEZE                tests/ を読み取り専用化 + マニフェスト採取
     │  §4-3
     ▼
 IMPL ◀───┐            ソルバー呼び出し #3..（実装）
     │     │           書込許可: files_write のみ
     ▼     │
 VERIFY ───┘ 不合格かつ attempt < max_attempts
     │  §4-4
     ▼
 GREEN                 コミット + タグ + contracts 確定
```

**位相ごとにソルバーの呼び出しを分ける**のは、テストを書く文脈と実装を書く文脈を
混ぜないため。TEST_WRITE のソルバーには `goal` を渡さない（acceptance と contracts のみ）。

## 4. 関門の判定条件

判定はすべて機械可読な事実に基づく。人間の判断が入るのは REVIEW_GATE のみ。

テスト実行は常に:

```
.venv/bin/pytest <files_test...> \
  --junitxml=.runner/report.xml \
  -p no:cacheprovider \
  --strict-markers -q
```

判定は **exit code ではなく junit XML** を読んで行う。

**`<testsuite>` は全部足す。最初の1つではない**（2026-09-02 修正）。pytest は1回の実行に
`<testsuite>` を1つしか書かないので、**「最初の suite」と「レポート全体」は同じもので、
区別する理由が存在しなかった** ── `root.find("testsuite")` は正しく見えていた。
vitest は**テストファイルごとに1つ**書く。VERIFY は `tests/` 全体を渡すので、
複数ファイルなら1ファイル分しか数えないことになる。実測（2ファイル・3テスト・1失敗）:

```
古い読み方 : tests 1  failures 1     ← 失敗した1ファイルだけ
新しい読み方: tests 3  failures 1     ← 正しい
```

しかも vitest の suite 順は**完了順**で固定されない。上の実行はたまたま失敗ファイルが
先だったが、逆なら **2テスト・0失敗** を返す ── **VERIFY が落ちている suite を緑と呼ぶ。**
非決定的に偽陽性を出す関門であり、2言語目を入れるまで**そこに在ったことすら分からなかった**。

### 4-1. RED_GATE（BOOTSTRAP 1-2 の実装）

以下を**すべて**満たすときのみ合格:

| # | 条件 | 防ぐもの |
|---|---|---|
| R1 | 収集されたテスト数 == `expected_tests` | テスト0件 / 水増し / 不足 |
| R2 | `<error>` 要素が **0 件** | 収集エラー・ImportError を red と誤認 |
| R3 | `skipped` が **0 件** | 全 skip の exit 0 |
| R4 | 全テストが `<failure>` を持つ | 一部が既に通っている＝テストが自明 |
| R5 | 全 `<failure>` の `type` が `AssertionError` または `Failed` のみ | 下記 |

**R5 が本体。** `ImportError` / `ModuleNotFoundError` / `AttributeError` / `TypeError` /
`NameError` での失敗は **red と認めない**。

これにより、赤の意味が「まだ実装がない」から
**「呼び出しは全部成立していて、値だけが違う」**に変わる。
副次的に、実装を1行も書く前に**契約のシグネチャが正しいことが検証される**。

**R4 は1件でも通れば止まる**。他に落ちる条件があっても救われない ── 通ったテストは
「落ちうること」を一度も示していないので、そのあと緑になっても意味が無いという理屈がそのまま
効く。受け入れ条件がこれを踏む道は2つあり、**両方とも計画時にしか直せない**:

1. 期待値がスタブでも出せる値（空文字・0・空リスト・引数そのまま）
2. 期待結果を**コード自身が生んだ2つの値の比較**として書く。
   `advance(p.state, catalog, 0.0) == p.state` がこれで、両辺とも同じ番兵になり通ってしまう
   （run 4 S1 で停止）。L8 の締め直しはこれを機械で捕まえるためのもの（§8）

**R4 はスタブの返り値に依存する**（2026-08-18 実測）。`normalize` の実装で、スタブが
`""` を返したところ「空文字入力→空文字出力」の境界条件2件が**正解してしまい** R4 で停止した。
別の実行でスタブが `"__stub__"` を返したときは全件落ちた。つまり R4 の成否は、
スタブが**どの正解とも一致しない値**を返すかどうかで決まる。したがって STUB のブリーフは
「型が合っていて間違った値」では不十分で、**目立つ番兵値**を明示的に要求しなければならない
（§5）。空・ゼロ・既定値・引数そのままは、いずれもどこかの入力に対する正解なので禁止する。

不合格時の扱い:
- R5 違反（AttributeError 等）→ STUB をやり直させる（`stub_attempts` 上限 2）
- R1 違反 → テストと `expected_tests` の不一致。**プランナーへエスカレーション**
- R4 違反（スタブが通ってしまった）→ テストが自明。**プランナーへエスカレーション**

### 4-2. REVIEW_GATE（任意・既定 ON）

ランナーは `files_test` の内容と `acceptance` を並べた差分を出力して停止する。
人間は「このテストは受け入れ条件を符号化しているか」だけを見る。**実装は見ない。**

- 承認 → `runner approve --step <id>` で FREEZE へ
- 却下 → TEST_WRITE からやり直し（`review_rejections` を台帳に記録）

これは BOOTSTRAP 1-1 の唯一の漏れ口（受け入れ条件→テストコードの翻訳を
ソルバーが単独で行う）に対する関門。1ステップあたり数分で、凍結前の1回だけ。

`review_gate: false` にできるが、その場合 `acceptance` は全項目が
具体値（given の数値と then の期待値）を持つことをリンタが要求する（§8）。

### 4-3. FREEZE（BOOTSTRAP 1-3 の実装）

**主機構（剥奪）:**
```
chown -R runner:runner tests/
chmod -R a-w tests/
chmod a-w conftest.py pytest.ini pyproject.toml   # 存在するもの
```

**トリップワイヤ（検知）** — `.runner/freeze/<step_id>.json` に記録:

| 記録項目 | 検出できる細工 |
|---|---|
| `files_test` 各ファイルの sha256 | 直接の書き換え |
| 全階層の `conftest.py` の sha256 と**存在しないパスの一覧** | conftest の新規追加による fixture 差し替え |
| `pytest.ini` / `pyproject.toml` / `tox.ini` / `setup.cfg` の sha256 | `addopts`、収集ルート、マーカーの改変 |
| `--collect-only -q` のテスト ID 全集合の sha256 | 件数を保ったままの入れ替え |
| `expected_tests` | 削除 |
| `pip freeze` の sha256 | 環境の変更 |

「存在しないパスの一覧」は重要。ハッシュは**あるファイル**しか守らないので、
`tests/conftest.py` や リポジトリ直下の `sitecustomize.py` の**新規作成**が素通りする。

### 4-4. VERIFY（IMPL の各試行後）

順に判定し、最初に落ちた時点で打ち切る:

1. **凍結整合** — `.runner/freeze/<step_id>.json` を再照合。1つでも不一致 → **即エスカレーション**（リトライしない。テストに手を入れた事実は試行回数の問題ではない）
2. **経路許可** — `git status --porcelain --untracked-files=all` の全パスが `files_write` に含まれるか。含まれないパスが1つでもあれば → 即エスカレーション
3. **テスト結果** — **`tests/` 全体**を走らせ、`<error>` 0、`skipped` 0、`<failure>` 0
4. 3 が不合格 → `attempt += 1`。試行予定（§4-4-1）が残っていれば IMPL に戻る

2 は権限だけでは足りない部分（`src/` 内で宣言外のファイルを作る）を埋めるための検知。
`.git/` と `tests/` と `plan/` は権限で既に守られている。

**3 で全スイートを走らせるのは、ステップの完了が2つの半分でできているから。**
「このステップのテストが通る」（FAIL_TO_PASS）と「通っていたテストが1つも落ちない」
（PASS_TO_PASS）。**当初は前半しか見ておらず**、あるステップが前のステップを壊しても
ランナーは緑と呼んで進んでいた。検知していたのではなく、たまたま壊れていなかった。

**skip は緑ではない。** 上の 3 は最初からそう書いてあったが、**実装は `skipped` を
見ていなかった**（`TestRun.green` が `tests > 0 and failures == 0 and errors == 0`
だけを見ていた。2026-08-21 修正）。RED_GATE は R3 で skip を拒否するのに VERIFY は
しない、という非対称は PASS_TO_PASS の穴になる ── 後続の実装が動的な skip 条件
（`skipif` や `importorskip`）を成立させると、以前は通っていたテストが**走らないまま
素通り**し、黙って縮んだスイートでステップが緑になる。判定に入れるだけでなく、
**台帳の VERIFY レコードに `skipped` を残す**。緑は事後に台帳だけで証明できる必要があり、
「failure が 0 件」はテストが走ったことの証明にならないため。
skip で止まった場合はソルバーへのフィードバックに**走らなかったテストを名指しする**
（pytest 自身はその実行を成功と呼ぶので、出力を渡すだけでは手掛かりが無い）。

**RED_GATE は逆に、そのステップのテストだけを走らせる**（R1 の収集数が
`expected_tests` と一致することに意味を持たせるため）。関門ごとに対象が違うのは意図的で、
それぞれの仕事が違う。

前のステップのテストが落ちた場合、その事実を**ソルバーへのフィードバックに明示する**。
`tests/` は凍結されていて編集できないので、直せるのは実装だけであり、
それを言わないと直しようのない指示になる。`max_attempts` を使い切った場合は
エスカレーションの理由に**壊した相手を名指しする** ── 「まだ実装できていない」と
「前のステップを壊さずには実装できない」は別の問題で、後者は受け入れ条件どうしの
矛盾の可能性があり、ソルバーが決めることではないため。

### 4-4-1. 試行の始め方と、ソルバーの段

**1ステップの試行予定は「試行回数 × ソルバー段」で決まる。** ランナーは
`attempt_schedule(step)` で「何回目をどのバックエンドが走るか」の一覧を先に作り、
それが尽きるまで IMPL ⇄ VERIFY を回す。

**試行回数** — `max_attempts`（ステップ単位）。最上位 `"limits": {"attempts": n}` で
**全ステップを一括で上書き**できる（0 は「プランに従う」）。一括の口が要るのは、
適切な回数が**誰が試行の代金を払うか**で決まるのに、プランを書く時点のプランナーは
それを知らないため。枠を消費するソルバーなら 3 が正しく、ローカルのソルバーなら試行の
原価は実時間だけなので、10回でもエスカレーション1回が買う**プランナー呼び出し1回より
安い**。ソルバーを差し替えるたびに11ステップを書き直すのは、プランの側の問題ではない。

**始め方** — `"policy": {"retry": "repair" | "resample"}`（ステップ単位の `"retry"` が優先）。

| | 作業ツリー | 直前の失敗の伝達 |
|---|---|---|
| `repair`（既定） | 失敗したまま引き継ぐ | 渡す |
| `resample` | HEAD に戻す | 渡さない（RED_GATE の失敗のみ） |

`resample` は §6-2 が**エスカレーションの粒度で既に採っている方針** ──
「失敗した実装はソルバーに渡さない。壊れた方針への固着を避けるため」── を、
1つ内側の粒度に降ろしたもの。自分の失敗を読んで直せるソルバーには `repair` が正しく、
そうでないソルバーでは損傷が累積し、後の試行ほど悪い木から始まる。そしてランナーは
**厳密な検証器**なので、同じ予算を「N回の独立した抽選」に使う選択肢が成立する ──
誤魔化せない関門に対する N 回の抽選は、弱いソルバーでは修復より強い。

巻き戻しは `git reset --hard` **ではない**。このステップのテストは書かれているが
まだコミットされていない（コミットは GREEN）ので、reset は満たそうとしている当の
テストを消す。戻すのは `files_write` のパスだけで、それは経路許可（4-4 の 2）が
「変わったのはここだけ」と既に確認した集合と同一。台帳に `DISCARD` を残す。

**時間切れ** — IMPL でソルバーが `timeouts.solver` 以内に終わらなかった試行（solver-run の
終了コード 124）は、試行1回分の失敗として数え、次の試行へ進む。書きかけの作業は
`repair` でも捨てる。途中で止まったファイルは修理の土台にならないからだ。凍結の
照合と経路許可は成功した試行と同じく通し、破っていれば今までどおり止める。
台帳に `SOLVER_TIMEOUT` を残し、次の試行のブリーフに時間切れだったことを伝える。
試行を使い切ったときの理由には、何回が時間切れだったかを書く。TEST_WRITE と STUB の
時間切れ、および runner 側の上限（`BACKSTOP_MARGIN`）に当たった場合は、ステップを止める。
後者はソルバーのプロセスがまだ生きているかもしれないからだ。

**ソルバー段** — 最上位 `"solver_tiers"`。**既定は `["claude"]`**（§7 末尾）で、
段は1つ。2段にするときは `"solver_tiers": ["local", "claude"]` のように書く。
先頭の段が**試行を使い切ってから**、次の段がそのステップを初めて見る。交互ではない
── 早すぎる引き渡しは、安い側がまだ試し終えていない仕事に高い側を使う。段が変わる回は
作業ツリーを捨てるが、**失敗の文面は渡す**（引き渡しは「前任の書きかけを継ぐこと」では
ないが、既に分かっていることを捨てる理由も無い）。

段を2つ置く理由は費用ではなく**費用の比較**にある。試行を使い切った先にあるのは
エスカレーションで、それは**プランナー呼び出し**を1回使う。2段目のソルバーは追加の
出費ではなく、次に起きる2つのことのうち安い方。

ランナーが渡すのは**バックエンドの名前だけで、コマンドではない**。名前から実体への
対応は root 所有の `bin/solver-run` が持ち（`/srv/loop/bin/solver-<name>`、root 所有
0755、引数は `<brief> <seconds>`）、ランナーはバックエンドを**追加できず**、sudo を
持つ人間が既に置いたものを指名できるだけ。名前は `[a-z0-9]+` で検査する ── パスに
埋め込まれるため。走ったバックエンド名は台帳の `ADOPT` / `VERIFY` と ESCALATION.md に
残る。どの段が緑を出したのかは、事後に台帳だけで答えられる必要がある。

| 名前 | 実体 | コマンドの実行 | 資格情報 |
|---|---|---|---|
| `claude` | `solver-claude`（Claude Code。`Read` `Write` `Edit` のみ） | できない | `/etc/loop/solver.env` |
| `local` | `solver-local`（ローカルの llama.cpp サーバ。`docs/LOCAL_SOLVER.md`） | できない | 無い |
| `codex` | `solver-run` 自身が起動する Codex CLI | サンドボックスの中でできる | `/home/solver/.codex` |

コマンドを実行できないバックエンドだけで段を組むと、ランナーは計画のブリーフに
「ソルバーはコマンドを実行できない」と書き足す。プランナーが「このコマンドで
確かめてから終えよ」と CONTEXT.md に書き、ソルバーが試行をそれに使うのを防ぐ。

### 4-5. GREEN

```
ledger GREEN
git add -A
git commit -m "step(<id>): <goal 1行>"
git tag step/<id>
```

`GREEN` は実装と同じコミットに含める。次のステップのコミットに持ち越すと、最終ステップには
持ち越し先がなく、bare リポジトリとホスト側ミラーの台帳が常に1ステップ遅れるため。

`contracts.provides` を `.runner/contracts/<id>.json` に確定保存。以降のステップは
**この確定済み contracts のみ**を参照する（tasks.json の記述ではなく）。

続けて `origin`（`/srv/loop/repo.git`）へ push する（`publish()`。`plan apply` の直後にも
同じことをする）。狙いは、緑になったステップを `reset` / `clean` の射程から外すこと。

**push の失敗はステップを落とさない。** 緑の根拠はテストが通ったことであって、
ミラーが受理したことではない。台帳に `PUBLISH_FAILED` を残して先へ進む。
ブランチは `--force` を付けずに押す ── ランナーは履歴を書き換えないので、
non-fast-forward は**この仕様が知らない何かが起きた印**であり、上書きは誤り。
タグだけは `tag -f` で動きうるので force で押す。

`repo.git` は同じ VHDX の中にあるので、**これはバックアップではない**。
ディスクごと失う場合に備える複製はホストが SSH で引く（`host/loop-pull.cmd`）。
**押すのではなく引く**のは、外に届く認証情報をサンドボックス内に置かないため。

最後のステップ後は `ALL_GREEN` と計画のハッシュを台帳に書き、台帳だけの完了コミットを
作ってもう一度 publish する。これがホスト側GUIの予定レビューを発生させる客観的事実になる。
同じ計画ハッシュの `ALL_GREEN` が**コミット済みなら**完了コミットを重ねない。判定は台帳
ファイルではなく `git show HEAD:plan/ledger.jsonl` を読む ── 台帳に書いた直後にコミットが
失敗した場合、「ファイルに書いてあるから済んだ」と見なすと**二度と publish されず**、
この仕組みが直したはずの症状（ミラーが完了を映さない）に戻るため。記録がファイルにだけ
ある場合は、追記せずコミットだけをやり直す。

### 4-6. ランナー自身のテスト（2026-08-21）

`runner/tests/`。**標準ライブラリだけ**で書き、題材側の venv には依存しない
（venv は bootstrap のたびに捨てるものなので、そこに engine のテストをぶら下げない）。

```
python3 -m unittest discover -s runner/tests
```

対象は `parse_junit` ── 関門の算術が実際に住んでいる場所で、RED_GATE も VERIFY も
これに質問しているだけ。固定しているのは5つの判定（全件成功 / failure / error /
skip / 0件）と、報告が読めない3つの場合（ファイルが無い / XML が壊れている /
XML ではあるが報告ではない）。**読めないものは常に error であって不在ではない**
── 読めなかった報告を「failure 0 件」と読むと、走らなかった実行でステップが緑になる。

ここにテストが1本も無かった代償は実測で2回出ている。R5 が `message` 属性を読んで
まともなアサーションを拒否した件と、`green` が skip を無視していた件で、
どちらも「読めば分かる」種類の欠陥だった。

## 5. ブリーフの組み立て（BOOTSTRAP 1-5 の実装）

ソルバーに渡す入力は、位相ごとに以下だけ。**tasks.json 全体は渡さない。**

```
[TEST_WRITE]
  plan/CONTEXT.md（静的・100行以内）
  当該ステップの acceptance[]
  depends_on から解決した contracts（.runner/contracts/*.json）
  files_test のパス一覧
  ※ goal は渡さない

[STUB]
  当該ステップの contracts.provides
  files_write のパス一覧
  ※ acceptance も goal も渡さない（テストを覗いて誤魔化す余地を消す）

[IMPL]
  plan/CONTEXT.md
  当該ステップの goal
  depends_on から解決した contracts
  凍結済みテストの内容（読み取り専用）
  直近の失敗した pytest 出力（当該ステップ内の前試行のみ）
  files_write のパス一覧
```

### 5-1. STUB はソルバーに書かせない（2026-09-21 変更）

**ランナーが組み立てる。** スタブの仕事は「形は正しく、値は全部間違っている」の一つだけで、
そこに判断は要らない。`contracts.provides` が署名も型の中身も置き場も持っており、
L14 と L15 はまさにそれを保証するために在る。

8回の run はソルバーに書かせていた。run 8 の S1 は**正解を返すスタブ**で4回止まっている ──
`return false`、そして温度を下げたあとは
`return {resource: 0, generators: {}, lastUpdate: 0}`（createGame の正しい初期状態）。
ブリーフは「空・ゼロ・既定値を返すな」と明示している。**届いて、読めて、無視された。**

**モデルが無視できる指示より、届かない規則のほうが強い。** `sudo` を監視せず取り上げるのと
同じ判断。

- **boolean だけが例外。** どの boolean も何かの正解なので「正しい型の間違った値」が
  存在しない。そこだけ異物（`"__stub__" as unknown as boolean`）を返す。数値・文字列・
  配列・オブジェクトは自分の番兵を持つ（文字列にすると `TypeError` になり R5 が弾く）
- **辞書型には受け入れ条件が引用しているキーを入れる。** `CATALOG.cursor.rate` は
  cursor が無ければ比較の前に落ちて R5 になる。契約はキーを言えない
  （`Record<string, GeneratorDef>` は型であって名簿ではない）が、基準は言える。
  **これは下の「STUB に acceptance を渡さない」に触れない** ── あの規則は*モデル*から
  基準を遠ざけるもので、ここでは何もモデルに見せず、値は全部番兵のまま。
  `__stub__` を併置するのは、基準の言うキーだけにすると**キー集合の比較が一致する**から
- **parse できないものは生成しない。** `None` を返してソルバーに戻す。コンパイルできない
  スタブを作るのは、置き換えた問題より悪い。Python は現状すべてソルバーのまま

配線前に、生成物を実際に vitest にかけて確認した ── **`toBe(false)` を期待するテストも
`toBe(true)` を期待するテストも落ちる。** モデルが値を選んでいる限り boolean には
持たせられなかった性質。

### 5-2. ソルバーに渡さないもの

STUB のブリーフには**シグネチャ以外を一切載せない**（ソルバーに書かせる場合）。
意味を運ぶものを載せるとソルバーはそれを忠実に実装し、その受け入れ条件は RED_GATE で
通ってしまう（`contracts` に `raises` を書いて実際にそうなった。2026-08-18）。
`invariants` も渡さない。


`invariants` は **TEST_WRITE のブリーフに載る**。したがって不変条件は
**公開契約を通して観測できるもの**でなければならない。実装構造を述べた不変条件
（例:「`normalize()` に委譲し自前では正規化しない」）を書くと、ソルバーは
モジュール内部を覗くテストを書き、シグネチャだけのスタブに対して `AttributeError` で
落ちる ── R5 が「assertion ではない」として正しく弾く（S2 で実際に踏んだ。2026-08-18）。
委譲のような実装上の要求は `goal` に書く。`goal` は IMPL にしか渡らない。
同じブリーフで、番兵値が**署名の述べる形**を持つことも要求する（2026-08-21 追加）
── タプルは注釈と同じ要素数、辞書は呼び出し側が引くキー、データクラスは全フィールド。
テストはアサーションの前に返り値を分解するので、分解できない値は
**赤いテストではなく壊れた呼び出し**になり、R5 が拒否して誰も直せなくなる（§8 L14）。

同じブリーフで**目立つ番兵値**を明示的に要求すること（§4-1）。「型が合っていて間違った値」
だけでは、ソルバーが `""` や `0` を選んだ瞬間に境界条件が正解してしまい R4 で止まる。
併せて「検証・型チェック・分岐を一切書かない」ことも指示する。

**入力量はステップ番号に依存しない**（`depends_on` の数にのみ依存する）。
BOOTSTRAP 1-5 の「1回あたりの入力量が一定」はここで実現される。

CONTEXT.md に contracts を蓄積してはならない。CONTEXT.md は静的。

### 6-1. 台帳 `plan/ledger.jsonl`（追記専用・runner 所有）

{"ts":"2026-08-13T10:22:31Z","step":"03","phase":"RED_GATE","result":"pass","tests":5}

**プランナーはセッションを跨いで記憶を失う**ので、これが唯一の履歴。
再開時、ランナーは台帳から現在位相を復元する。

### 6-2. エスカレーション自体の上限

BOOTSTRAP 1-4 は試行の上限しか定めていないため、(a) を繰り返す外側のループが無限になる。

> **同一ステップの `escalation_no` が 2 以上のとき、(a)「goal の書き方を締める」を禁止する。**
> 選べるのは (b) 受け入れ条件の書き直し、または (c) 上流からの作り直しのみ。

ランナーは ESCALATION.md にこの制約を明記して出力する（プランナーが忘れても効くように）。

**実装済み（2026-08-19）。** `LIMITS["escalations"]`、既定 1。
`tasks.json` の最上位 `"limits": {"escalations": n}` で上書きできる。

- **回数は台帳から数える**（`escalation_count()`）。メモリ上のカウンタではないのは、
  上限が意味を持つのは**プロセスが終わる場面**だから ── VM の停止、`reset`、翌日の再開。
  これは `reset` が台帳を巻き戻すのをやめた理由でもある。**reset が消す記録から数える
  上限は上限ではない**
- ESCALATION.md の文面は回数で切り替わる。上限を超えた回は
  「(a) はもう選べない。(b) か (c) のみで、どちらも人間の判断」と書き出す
- 明記するだけでなく `run --all` 側でも判定する。**書いてあることに従わせるのではなく、
  そこから先に進む経路を無くす**

**(b) を実行する動詞が無い（未解決・run 7 で踏んだ）。** 上の制約は「(b) 受け入れ基準の
書き換えは人間の判断」と言うが、人間がそれを行う手段は `plan/tasks.json` の手編集しかない。
そして `cmd_reset` は `git reset --hard HEAD` を打ち、**台帳だけ**を明示的に退避する
（§6-2 の理由による）ので、**コミットしていない基準の書き換えは `reset` で消える**。
順序は「編集 → コミット → `reset <id>` → `run <id>`」。動詞を足すか、`reset` の退避対象に
`plan/` を含めるかは未決。

```
git checkout -b escalate/<step_id>/<escalation_no>
git add -A && git commit -m "escalated attempt"
git checkout <last green> && git reset --hard
```

失敗した実装は**ブランチに保存し、プランナーだけが読む**。
再開時のソルバーには渡さない ── 壊れた方針への固着を避けるため。
ソルバーは常に「最後の green + 書き直されたステップ」からやり直す。

#### `PLANNER_ESCALATION.md` ── 逆向きの一枚（2026-09-02 追加）

プランナーが「自分に許された変更では直せない」と判断したときに書く `ESCALATE.md` は、
`planner/out/` にできる ── **リポジトリの外**である。当初はそれを `plan apply` が
標準出力に印字するだけだったので、**コミットされず、ホストのミラーにも来ず、
ダッシュボードにも出なかった。** `plan apply` を叩いた端末にしか流れない。

**人間宛ての問いが、端末1つにしか届かないなら、人間宛てになっていない。**
ランナーが人間を呼ぶ道（`ESCALATION.md` → コミット → ミラー → 画面）は意図して
作られていたのに、**逆向きの道が無いことに誰も気づいていなかった** ── run 7 で

`plan apply` は `ESCALATE.md` を受け取ると、本文を `plan/PLANNER_ESCALATION.md` に
書き、コミットして publish する（印字は従来どおり）。

**2つのファイルは統合しない。** `ESCALATION.md` は `plan propose` が答える質問であり、
`plan propose` はそれが無ければ動かない。プランナーの拒否をそこに書けば、次の
`plan propose` が**既に答えの出た問いにもう一度答える**ことになる。意味が違い、
答え方も違うものは、別のファイルで別の要求として扱う。計画が適用された時点で
両方消える ── 適用されたこと自体が両方への答えだから。

### 6-5. プランナーの提案経路（2026-08-19 実装）

BOOTSTRAP 1-4 の (a) をプランナーが自走で行うための経路。**(b) と (c) は人間に戻す**という
区別を、指示ではなく機構で成立させる。

```
 ESCALATION.md（ランナーが書く）
     │
     ▼
 loop.py plan propose --step <id>
     │  ブリーフ = SYSTEM_SPEC.md + CONTEXT.md + tasks.json + ESCALATION.md
     │  planner-run（uid planner・使い捨て HOME・timeout）
     ▼
 /srv/loop/planner/out/     プランナーが書く。tasks.json / CONTEXT.md /
     │                      SYSTEM_SPEC.md / ESCALATE.md のみ
     ▼
 loop.py plan apply
     │  ファイル名の許可リスト → P1..P5 → リンタ L1..L11
     ├── 不合格 → exit 2。out/ はそのまま残る（人間が読めるように）
     ├── ESCALATE.md → exit 3。適用せず人間へ
     ▼
 plan/ に反映 → git commit → out/ を空にする → ESCALATION.md を消す
```

**「差分が3ファイルに収まっているか」はファイル名の許可リストで実装する。**
差分の検査ではない。4つ目のファイルを書いた提案が現れてから是非を論じる、という状態が
そもそも発生しない ── 送り先が3つしか定義されていないため。`ESCALATE.md` は4つ目の
名前だが、**どこにも適用されない**ので性質は変わらない。

既存ステップについて拒否する変更（`check_proposal`）:

| # | 拒否する内容 | 理由 |
|---|---|---|
| P1 | ステップの削除 | 受け入れ条件の削除にあたる。(c) は人間の判断 |
| P2 | `acceptance` の変更 | (b) は人間の判断 |
| P3 | `expected_tests` の引き下げ | RED_GATE R1 が数える値。同じ条件に対してテストを減らす |
| P4 | `review_gate` を true → false | 人間の目を機械的に外す変更 |
| P5 | **green 済みステップの定義変更** | 何を検証したかの記録。書き換えると台帳が事実と食い違う |

**P2 と P3 の例外 ── R4 で空と分かった条件の削除。** 開いているエスカレーションが
RED_GATE の R4（スタブに対して通るテスト）なら、そのステップに限り、`acceptance` の
項目を**消す**ことを許す。スタブに対して通るテストは落ちうることを一度も示しておらず、
その条件は環境が持つものなど、どのステップのコードも決めないものを確かめている。
緩める対象ではなく、最初から何も確かめていない。

- 許すのは消すことだけ。残す項目は順番も中身も変えない。書き換えや追加は P2 のまま
- 消せる数は、R4 で通ったテストの数まで。`escalate` がその数を台帳の `ESCALATED` に
  `r4_passing` として残し、`check_proposal` はそこから読む
- `expected_tests` は、消した数まで下げてよい
- どの項目を消したかまでは機械で確かめられないので、数で縛る。改訂のブリーフと
  ESCALATION.md には、この手と上限を書く

**ステップの追加は許可する。**計画が伸びるのはそれ以外にないため。
`goal` / `contracts` / `files_write` / `files_test` / `depends_on` / `max_attempts` は
自由に書き換えてよい ── これが (a)「実装が悪いので goal を締める」の中身。

比較は `json.dumps(..., sort_keys=True)` の一致で行う。インデントの付け直しやキーの
並べ替えを変更と読まないため。

補足2点:

- **ブリーフには acceptance を含む計画全体を渡す。**これは漏洩ではない。プランナーは
  受け入れ条件の**著者**であり、BOOTSTRAP 1-1 が分けているのは
  「条件を書く主体」と「コードを書く主体」。`plan/` の 0700 が買っているのは
  「プランナーが `tasks.json` を**書けない**」ことだけで、読めないことではない
- **`SYSTEM_SPEC.md` は `plan/` の下に置く**（BOOTSTRAP のファイル表からの逸脱）。
  リポジトリ直下はソルバーから読める ── 読めないと作業できない ── ので、
  そこに仕様を置くとブリーフと並ぶ第二の入力経路になり、1ステップ分の契約しか
  渡していないはずのソルバーが全体設計を読めてしまう。`plan/` は 0700 runner

計画が存在するようになる唯一の経路。形は他のプランナー呼び出しと同一 ──

### 6-7. 提案の自己修正ループ（2026-08-19）

**要件は作るものについて書く。この機械が受け付ける計画にするのはプランナーの仕事。**
その分担を成立させる機構。

```
 プランナー呼び出し
     ▼
 out/ を検査（`proposal_problems()` = plan apply が使うのと同じ関数）
     ├── 違反なし → 終わり
     └── 違反あり → 違反を添えて呼び直す（out/ は消さない）
                    上限 LIMITS["revisions"]（既定3）
```

3点、意図がある。

- **検査は `plan apply` と同一の関数で行う。** 別実装にすると必ず食い違い、
  「プランナーに直せと言った内容」と「実際に拒否する条件」がずれる
- **リトライの間、out/ のファイルは消さない。** プランナーは記憶を持たないので、
  消すと禁止事項だけを頼りに一から書き直すことになる。残しておけば、
  自分が書いた計画を読んで直せる ── 安いし、別の違反と交換する確率も下がる
- **プランナーに新しい権限は要らない。** リンタを実行するのはランナーで、
  プランナーは結果を渡されるだけ。剥奪の原則は崩れない

**許可外のファイル名は、ランナーが消してから指摘する。** プランナーは作成と編集しかできず
削除できないので、「消してください」は従いようのない指示になる（B3）。

**ただし、消したこと自体は違反として数えない。** 削除した時点でその条件はもう存在せず、
`read_proposal()` は許可された3名しか見ないので、消えたファイルが `plan apply` に届く
経路は無い。それでも1回失敗にすると、**ランナーが既に解消した状態のために試行を1回使う**
ことになる（run 7 のブートストラップは、これだけを理由に4回のうち1回を失った）。
実装は「他の理由で落ちる試行のフィードバックに同乗させる注記」で、単独では落とさない。
台帳には `PLAN_PRUNED` として残る。

計画本体を綴り違いのファイル名で書いた場合は、削除の結果 `tasks.json` が無くなるので
`proposal_problems()` が「必須ファイルが無い」として落とす ── **本当に問題がある場合は、
消したことではなく消えた結果が捕まえる。**

#### なぜこれが要るのか

ブリーフの規則一覧（L2〜L12）は、**人間がランナーの挙動を手で書き写したもの**でしかない。
実際、最初の版は L12 が抜けており、プランナーは10ステップ全部を `incgame/` に置いた計画を
出した ── 書いていないことは伝わらない。次に何が抜けるかは分からない。

**このループが本当の答えである。** ブリーフが言い忘れたことも、リンタは必ず捕まえ、
その結果がプランナーに渡る。ブリーフの規則一覧は往復を1回減らす最適化であって、
保証ではない。

併せて、ブリーフには**機械から読んだ環境の事実**を載せる（`environment_facts()`）:
インタプリタと pytest のバージョン、ランナーが実際に打つテストコマンド、
`plan/` を除いたツリーの実状、`conftest.py` の中身。手で書き写す理由がなく、
書き写せば古くなるものは、その場で読む。

**しかし「人間が最後に打つコマンド」を述べる行が無い（未解決・run 7 で踏んだ）。**
上の一覧を読み直すと、**テストの走らせ方は4つの角度から正確に伝えている**のに、
成果物の起動のされ方はどこにも無い。run 7 の要件1行目は
「Windows 上で `python -m idlegame` の一つのコマンドで画面が開くこと」だったが、
プランナーは pytest の慣習どおり `src/idlegame/` に置き、`conftest.py` に
`sys.path.insert(0, .../"src")` を書いた。42テストは全部緑になり、**`python -m idlegame`
は `No module named idlegame` で落ちた。**

**これを捕まえられる関門は、いまの設計には存在しない。** 受け入れ条件は pytest の表明
として書かれ、pytest は `conftest.py` を読み、`conftest.py` が `sys.path` を捏造する ──
**成果物の起動経路は、テストが必ず迂回する経路**である。受け入れ条件をいくら書き足しても、
pytest から検査するかぎり同じ穴を通る。REVIEW_GATE（人間が遊ぶ）でしか露見しない。

直す方向は2つあり、両方要るとみている:

- `environment_facts()` に**成果物がどう起動されるか**を足す。要件が起動コマンドを
  述べているなら、それをそのまま事実として渡す
- **起動そのものを機械が確かめる。** pytest の中から `subprocess` で
  「素の Python」に `python -m <pkg> --version` 相当を打たせれば、`conftest.py` を
  経由しない経路を1本だけ検査できる。GUI を開かずに import 可能性だけ見る形

これは L15・L16 と同じ根から3度目に出た同じ話 ── **ブリーフに載らない場所に書いた
規則は、無いのと同じ。**

BOOTSTRAP.md §3 の記述に対し、ランナーが機構として動くために以下が必須:

```json
{

  "kind": "unit",
  "goal": "...",
  "depends_on": ["01", "02"],
  "acceptance": [
    {"case": "normal",   "given": "...", "then": "..."},
    {"case": "boundary", "given": "...", "then": "..."},
    {"case": "error",    "given": "...", "then": "..."}
  ],
  "contracts": {
    "provides": ["def tokenize(text: str) -> list[Token]", "..."],
    "invariants": ["同じ入力に対し常に同じ出力", "空文字列では空リスト"]
  },
  "files_write": ["src/pkg/tokenizer.py"],
  "files_test":  ["tests/test_tokenizer.py"],
  "expected_tests": 5,
  "max_attempts": 3,
  "review_gate": true
}
```

追加の理由:

| フィールド | なぜ必要か |
|---|---|
| `depends_on` | 番号順だけでは 1-4(c) の「破棄すべき green」を機械計算できない |
| `expected_tests` | R1（テスト0件・削除の検出）が実装できない |
| `kind: "integration"` | 結合ステップを**終盤だけでなく早期にも**置くための識別。リンタが配置を検査する |
| `contracts.invariants` | 型だけでは意味が運べず、後続が誤解したまま green になる |
| `acceptance` の構造化 | 正常/境界/異常の充足をリンタが検査できる |

最上位（ステップの外）に置ける設定が5つある。いずれも省略可で、
**既知のキーだけを読む** ── 綴りを間違えた設定が黙って無視されるのを防ぐため。

```json
{
  "language":     "python",
  "timeouts":     {"test": 120, "solver": 960, "planner": 1800},
  "limits":       {"escalations": 1, "attempts": 0},
  "policy":       {"retry": "repair"},
  "solver_tiers": ["claude"],
  "steps": [ ... ]
}
```

`timeouts` の各値の根拠は §11-4 と `bin/solver-run`、`limits.escalations` は §6-2、
`limits.attempts` / `policy.retry` / `solver_tiers` は §4-4-1。

#### `language`（2026-09-02 追加）

`"python"` か `"typescript"`。**既定は `python`** ── これ以前に書かれた計画は全部それを
前提にしており、**計画は「何を検査したか」の記録なので、読み直して意味が変わってはいけない**。

上の4つと違い、**未知の値は既定に落とさず異常終了する。** 黙って Python になれば、
間違ったテストランナーが間違った拡張子に対して走り、**全ての関門が「一度も読んでいない
ファイル」について自信を持って報告する** ── 沈黙して間違うより、止まるほうがよい。

この設定が変えるのは4つだけ:

| | `python` | `typescript` |
|---|---|---|
| 判定を出すコマンド | `.venv/bin/pytest` | `node_modules/.bin/vitest run` |
| 凍結する拡張子（§4-3） | `.py` | `.ts` |
| パス → 名前（L15） | `src/pkg/e.py` → `pkg.e` | `src/pkg/e.ts` → `pkg/e` |
| 形の無い型（L14） | `dict`, `list`, ... | `Record`, `Array`, `any`, ... |

**変わらないものの方が本質的である。** junit レポートの読み方、全ての関門の算術、
書き込みフェンス、台帳、エスカレーションの規則、L14 の語彙以外の全リンタ規則 ──
規則はもともと言語非依存で、Python 的だったのはその**表現**だけだった。
L14 の本文がそう予告していたとおり（「A second language re-states it in its own type
syntax; the rule itself does not change」）。

TypeScript であって素の JavaScript でないのは L14 のため。契約は次のステップに渡す
**形**を述べなければならず、型構文を持たない言語ではそれができない。vitest は esbuild で
`.ts` をそのまま実行するので、ビルド段も `tsc` も要らない ── **型はここでは
「読まれるもの」であって、コンパイラが検査するものではない。**

後ろの3つは**プランナーが書くものではない**（BOOTSTRAP_RULES にも書くなと明示してある）。
どのソルバーが何回走るかは**プランが走る機械の性質**であって、プランの性質ではない。

**だから既定値のほうが本体で、`tasks.json` の指定は上書きにすぎない。**
ブートストラップが作るプランに `solver_tiers` は入らない（プランナーはバック
エンドの存在を知らされていない）ので、**新しいプランは全部、既定の段で走る**。

既定は `["claude"]`。3役がすべて Claude Code で動き、追加の機材も Claude 以外の
サブスクリプションも要らない。3役は同じ利用枠を使うので、上限に当たった呼び出しは
失敗として数えず、待ってからやり直す（`loop.py` の `QUOTA`）。
`local` と `codex` は、計画が `solver_tiers` で名前を挙げたときだけ使う。
値が不正なら `run` は起動前に止まる ── 綴りを損ねた `resmaple` が既定に落ちると、
測っているつもりのものと実際に走ったものが食い違い、しかも黙って食い違う。

## 8. tasks.json リンタ（`runner validate`）

**プランナーの出力に対する唯一の客観的関門。** 実行前に必ず通す。

| # | 検査 |
|---|---|
| L1 | JSON Schema 準拠 |
| L2 | `depends_on` が自分より若い id のみを参照し、循環がない |
| L3 | 各ステップの `contracts.requires` が、依存先のいずれかの `provides` に存在する |
| L4 | `files_write` が全ステップで重複しない（1ファイル1所有者） |
| L5 | `files_write` ∩ `files_test` == ∅ |
| L6 | `acceptance` に `normal` / `boundary` / `error` が最低1つずつ |
| L7 | `expected_tests` >= `acceptance` の件数 |
| L8 | `review_gate: false` のステップは、全 `acceptance` の **`then` が単独で**具体値を含む（**数値**・リテラル・例外型のいずれか。形容詞のみは不可） |
| ~~L9~~ | **廃止**（2026-08-21）。L13 が「最初のステップは skeleton」を要求した時点で恒真になった。番号は再利用しない |
| L10 | `kind: "integration"` が最終ステップに1つ以上存在する |
| L11 | どのステップからも参照されない `provides` がない（デッドコントラクト） |
| L12 | `files_write` が `src/` 配下、`files_test` が `tests/` 配下（2026-08-19 追加） |
| L13 | **最初のステップが `kind: "skeleton"`**、かつ計画中にちょうど1つ（2026-08-19 追加） |
| L14 | `contracts.provides` の型注釈が**中身を述べている**こと。裸の `tuple`/`list`/`dict`/`set`（および `Tuple`/`Sequence`/`Mapping` 等）を拒否（2026-08-21 追加） |
| L15 | `contracts.provides` の各行が**居場所のモジュール**を述べ、それがそのステップ自身の `files_write` から導けること（2026-08-21 追加） |

**L9 は廃止した**（2026-08-21）。「最初の3ステップ以内に結合がある」を要求していたが、
L13 が「最初のステップが skeleton」を要求した時点で**二度と落ちない検査**になった。
落ちない検査は規則ではなく文章なので消す。L9 の意図（結合を終盤にしか置かない計画を防ぐ）は
L13 が完全に含んでいる。番号は識別子なので再利用しない ── 過去の実行の台帳が L9 を指している。

**L15 は L14 と同じ根**（BOOTSTRAP 1-5）から出ている。L14 が契約に**形**を述べさせ、
L15 は**居場所**を述べさせる。どちらも「後続に渡る1行だけで履行できること」。

**L16 の候補 ── 形だけを主張する受け入れ条件（未実装・run 7 で踏んだ）。**
`then` が呼び出しの副作用にも返り値の中身にも触れず、キーの集合・型・長さといった
**形**しか主張していない受け入れ条件は、**RED_GATE を原理的に通れない**。STUB は
シグネチャが正しい骨組みであることを義務づけられているので（§5 の STUB 規則）、
形だけの主張は STUB が必ず満たす ── R4 が正しく拒否し、どんな実装でも救えない。
**合格する世界が存在しない条件**であり、いまのリンタはこれを通す。

run 7 の S10 はこれで2回エスカレートし、上限を使い切って停止した:

```
then: set(table.keys()) == {'buy_cursor', 'buy_grandma'}
```

プランナーはエスカレーション1回目で原因を正しく見抜いたが、直し方を `goal` の散文に
書いた。**テストは `acceptance` から起こすので、その指示は届かない**（上の L15 と同じ
構図 ── ブリーフに載らない場所に書いても無い）。人間が `then` を購入の副作用まで
述べる形に直したところ、1回目で緑になった。

これは B3 の余計なファイル扱いと同じ形の話で、**後で必ず詰まると分かっているものを、
書けなくする**。検知ではなく剥奪。

テスト作成のブリーフは `goal` を意図的に含まない（テストは受け入れ条件から書かせる）。
含むのは `provides` なので、そこにモジュール名が無ければブリーフのどこにも無い。
run 4 の S1 は `from incgame.game import ...` と書いて収集に失敗した ── `game.py` は
8つ先のステップが作るモジュールで、この時点では存在しない（R1、エスカレ1回消費）。

**「ブリーフに `files_write` を足すだけ」で済ませる案は却下した。** 4ファイルを書く
ステップでは「どのシンボルがどのファイルか」が依然として推測になり、さらに**後続ステップは
それを一切見られない** ── `dep_contracts()` が渡すのは凍結された `provides` の文字列だけで、
モジュール名を持たない契約は下流では修復不能。情報は契約側に置くしかない。

**L13 は L9 が「歩く骨格」を名乗りながら実際にはそうでなかったことへの修正**
（2026-08-19 追加）。`integration` は「モジュールどうしが繋がる」であって
「初期状態から到達できる」ではない。**L1〜L12 を全部通し、10ステップ全部が緑になり、
全スイートが通ってなお、初期状態から到達できない**計画が実際に出た ── 資源の源は生産だけ、
生産には generator が要り、generator は資源で買う、という循環。どのステップも正しく、
**「始まること」についてのステップが1つも無かった**。

`skeleton` ステップは**薄い縦串**: システムが新品のときの状態から、公開 API を通って、
「この製品が仕事をしている」と人が認める地点まで。最初に、薄く作る（ハードコード可、
一般化不要）。後のステップがそれを深くする。

**L14 は BOOTSTRAP 1-5 の機構化**（2026-08-21 追加）。後続ステップに渡るのは
`provides` の1行だけなので、その1行から履行できない契約は契約になっていない。

```
def buy_max_affordable(...) -> tuple      ← 要素数がどこにも無い
スタブ: return ("__stub__",)               ← 1要素
テスト: result, count = buy_max_affordable(...)  → ValueError
```

**R5 は正しく止めている**（アサーションではなく呼び出しが壊れている）が、
**この時点では誰も直せない**。ソルバーが STUB 位相で見るのは署名だけで
（テストを見せれば期待値をハードコードできる）、プランナーは既に緑になった
ステップを P5 で編集できない。だから発生前に、リンタで**書けなくする**
── sudo を監視せず取り上げるのと同じ形。

対象は `provides` のみ（`requires` は L3 で `provides` と一致することが要求されるため）。
判定は**注釈の位置**（`->` または `:` の直後）だけを見る。同じ文字列に入る散文
（「... a list of ids」）を署名と取り違えないため。

`-> Purchase` のような**名前の付いた型のほうが、パラメタ化されたコンテナより良い**
（形に意味がある場合）。リンタが要求できるのは前者までではなく後者まで。

**これは言語非依存の規則「契約が形を決めていること」の Python 表現**である。
2言語目はそれぞれの型構文で言い直すことになる（言語結合点の9つ目）。

### 8-1. 各規則を買った失敗（2026-08-21 棚卸し）

規則は思いつきで足さない。**1つの規則は1つの観測された失敗が買っている。**
買った失敗を思い出せない規則は、消す候補になる。

| # | 買った失敗 |
|---|---|
| L1 | 設計（スキーマ準拠。これが無いと以降の検査が形を仮定できない） |
| L2 | 設計（前方参照を許すと、契約が存在しない順序で実行され得る） |
| L3 | 設計（1-5。requires が宙に浮いた計画は実行時に必ず止まる） |
| L4 | 設計（1ファイル2所有者は FREEZE と所有権の前提を壊す） |
| L5 | 設計（同じファイルが凍結対象かつ書込対象になる） |
| L6 | BOOTSTRAP §3 ルール2 |
| L7 | R1 が意味を持つために必要（受け入れ条件より少ないテスト数を宣言できてしまう） |
| L8 | **run 4 S1**：`then` が `s2 == p.state` で、両辺ともスタブの番兵なので R4 で停止。`given` と連結して検査していたこと、`@d` が変数名 `s2` の "2" に当たっていたことの2つが同時に効いていた |
| ~~L9~~ | 廃止。L13 に吸収 |
| L10 | 設計（最後に全体が繋がることを1度は確認する） |
| L11 | 設計（誰も使わない契約は分割の誤り。1-5 の後段） |
| L12 | **run 1〜2**：`src/` の外にパッケージを作られ、書込フェンスが効かない位置に置かれた |
| L13 | **run 3**：10ステップ全部が緑で全スイートも通りながら、初期状態から到達できない製品ができた |
| L14 | **run 3 S8**：`-> tuple` の要素数が伝わらず、スタブを分解できずに R5 で2回停止 |
| L15 | **run 4 S1**：モジュール名がブリーフのどこにも無く、import 先を推測して収集に失敗（R1） |

**リンタが強制できるのは構造だけ**で、中身が誠実かは検査できない。買えるのは
**その受け入れ条件が計画時に書かれること** ──「新規の状態から、○○すると、△△になる」は、
**最初の資源をどう得るか決めないと書けない**。穴は「人間が後から気づくもの」ではなく
「プランナーが計画中にぶつかるもの」に変わる。

緑になったあとは PASS_TO_PASS（§4-4）が骨格のテストを毎回走らせるので、
**一度通った縦串は落ちない**。double-loop TDD の外側テストに相当するが、
最後まで赤に保つのではなく最初から緑にする形 ── このランナーが実際に強制できるのはこちら。

**帰結: 既に走り始めた計画には後から満たせない。** 最初のステップが緑になっている計画に
骨格を差し込むことはできない（P5 が緑ステップの改変を拒否する）。L13 は
**計画の始め方についての規則**なので、始まっていない計画にしか適用できない。

**L12 は「フェンスが効かない計画を存在させない」ためのもの**（2026-08-19 追加）。
`set_writable()` が chmod するのも `adopt()` が歩くのも `src/` と `tests/` の2つだけなので、
それ以外に書くステップは**書き込みフェンスの対象外**になる。ワークスペースのルートは
group 書き込み可（ソルバーのパッチ適用に必要）なので、`src/` の隣にパッケージを作れば
「コードを書けないはずの位相」で書けてしまう。`assert_touched` が事後に捕まえるので
止まりはするが、**主機構がトリップワイヤに降格する**うえ、そこに作られたファイルは
solver 所有のまま残り、runner は chmod も掃除もできない。

最初の計画は既定でこれを間違える ──「パッケージはリポジトリ直下」は Python の
普通の書き方だから。だからブリーフの注意書きではなく、リンタが持つ規則にした。
実測でも、初回の bootstrap は10ステップ全部を `incgame/` に置いた（L2〜L11 は全通過）。

併せて、`contracts` の名前抽出が `def` しか見ておらず、`class GameState(...)` を
provides に書いた計画で **L3 が全滅する**バグを修正した（`def` と `class` の両方を見る）。
データモデルを最初のステップに置く計画は普通なので、これは実質すべての実計画に当たる。

## 9. CLI

当初の設計（未実装分を含む）:

```
runner validate                    # §8。それ以外の全コマンドの前提
runner run --step <id>             # 1ステップだけ回す
runner run --all                   # green が続く限り進み、停止条件で止まる
runner approve --step <id>         # REVIEW_GATE の承認
runner reject  --step <id> [--note] # REVIEW_GATE の却下
runner status                      # 台帳から各ステップの位相を表示
runner replan                      # ESCALATION.md 適用後、tasks.json を再検証して再開
```

**v1 で実際に存在するもの**（`sudo -u runner python3 /srv/loop/runner/loop.py …`）:

```
validate                     # §8
run <id> [--unvalidated]     # 1ステップ。--unvalidated はリンタ違反を台帳に書いて続行
run --all [--budget <分>]    # 停止条件に当たるまで回す
reset <id>                   # 止まったステップを捨て、最後の green に戻す
plan bootstrap [--from <path>]  # 要件 .md から最初の計画を起こさせる
plan propose [--step <id>]   # ESCALATION.md に対する改訂をプランナーに書かせる
plan show                    # 保留中の提案を、適用せずに表示する
plan apply                   # 提案を検査し、通れば plan/ に反映して commit
```

`plan` を3つの動詞に分けてあるのは意図的。`propose` は課金が発生し、`apply` は
ループが何に対して測られるかを書き換える。どちらも起こさずに提案を読めることが要る。

`approve` / `reject` / `status` / `replan` は未実装（§10）。

#### `run --all` の停止条件

外側のループは1本:

```
ステップを回す → green なら次へ
              → エスカレーションなら、上限内である限りプランナーに1回答えさせ、
                reset して同じステップをやり直す
```

止まるのは次の5つだけで、**すべてリポジトリか台帳に対する客観的事実**。
「うまくいっていないようだ」という判断は1つも入っていない（BOOTSTRAP 1-6）。

| 停止条件 | exit |
|---|---|
| 全ステップが green | 0 |
| そのステップのエスカレーション上限を使い切った（§6-2） | 2 |
| `plan apply` が提案を拒否した | 2 |
| プランナーが `ESCALATE.md` を書いた（(b) か (c)） | 3 |
| `--budget` の壁時計を使い切った（ステップの切れ目で判定） | 2 |

**提案が妥当かどうかをここでは一切判定しない。** 判定するのは `plan apply` で、
やり方は機械的。この分離があるから、外側のループを無人で回してよいことになる。

計画は毎周読み直す。直前に適用された提案が、これから走るステップを書き換えている
可能性があるため。green 済みのステップは台帳から判別して飛ばすので、
**中断してもステップ境界からは再開できる**（位相の途中からは §11-5 のまま未対応）。

### 終了コード

| code | 意味 |
|---|---|
| 0 | 対象範囲すべて green |
| 10 | REVIEW_GATE で人間待ち |
| 20 | エスカレーション（`ESCALATION.md` を参照） |
| 30 | リンタ不合格（tasks.json が不正） |
| 40 | 環境異常（venv 不在、権限設定の不備、プロキシ不通など） |

**exit 0 以外はすべて人間に戻る。** 自動で先に進む経路を作らないこと。

v1 の実装はこの表をまだ使っておらず、`0 / 1 / 2 / 3` の4値で返す
（0 成功、1 前提不足、2 停止・拒否、3 プランナーが人間に差し戻した）。
`run --all` を書いた時点でも寄せなかった ── 4値で足りているうちに5値に増やすと、
呼び分ける側が無いまま番号だけが増える。REVIEW_GATE を入れるときに見直す。

**なお 2026-08-19 の設計変更で、「exit 0 以外はすべて人間に戻る」は文字どおりではなくなった。**
エスカレーションのうち BOOTSTRAP 1-4 の (a) は `plan propose` → `plan apply` で
プランナーに戻る（§6-5）。人間に戻るのは (b) と (c)、すなわち `plan apply` が
拒否した場合（exit 2）とプランナー自身が `ESCALATE.md` を書いた場合（exit 3）。
**自動で先に進む経路は依然として存在しない** ── 進めるのは、受け入れ条件が
一字も変わっていないことを機械が確かめた提案だけ。

## 10. v1 でやらないこと

- ステップの並列実行
- ソルバーの複数モデル切り替え
- テスト実行のタイムアウト以外のリソース制限（cgroup 等）
- Web UI / 進捗ダッシュボード（`runner status` の標準出力で足りる）
- ランナー自身をこのループ方式で開発すること（**鶏卵になる。初版は手書きして捨てる**）

3. **`.venv` の作成タイミング** — プロビジョニング時に `runner` が作り、以降 solver からは
   読み取り専用。依存追加は CONTEXT.md の変更＝プランナーの仕事とする、で確定してよいか
4. **テスト実行のタイムアウト値** — 無限ループする実装が普通に出るので必須。
   ステップごとに指定させるか、全体固定（例 120s）か。
   **プランナー側は実測で 1800s に引き上げた**（2026-08-21）。
   引き上げと同時に、**その値を `solver-run` / `planner-run` へ渡すよう直した** ──

   実際に効く上限は動かない。run 5 は loop.py に 1800 と書いてある状態で

   加えて Claude Code はファイルを最後にまとめて書くので、打ち切られた計画呼び出しは
   **部分的な計画すら残さない**。低すぎる設定の代償が高すぎる設定より大きい
5. **VM が落ちた場合の再開の粒度** — §1-6。位相の途中（例: IMPL のソルバー実行中）で

# RUNNER_SPEC.md — ループランナー仕様

BOOTSTRAP.md の 1-2 / 1-3 / 1-5 と書き込みの柵を、**文章ではなく機構として**実装する
プログラムの仕様。設計を上流、中段、下流の3段でせき止め、モジュールを単位に実装する。

対象読者は、このランナーを実装し、運用する人間。

---

## 0. 位置づけ

### 0-1. 役の配置

| 主体 | 実体 | 実行場所 | 書けるもの | 見えるもの |
|---|---|---|---|---|
| プランナー | **Claude Code** | サンドボックス / `planner` ユーザー | `/srv/loop/planner/out` のみ | 仕様書、基本設計、詳細設計（ランナーが out/ に写したもの）、`src/` の既存のコード |
| ランナー | **このプログラム**（AI ではない） | サンドボックス / `runner` ユーザー | リポジトリ全体。git。sudo なし | すべて |
| ソルバー | **Claude Code**（ファイルの読み書きのみ。差し替え可。§4-4-1） | サンドボックス / `solver` ユーザー | 柵の中だけ。コマンドは実行できない | ランナーが組み立てた1モジュール分のブリーフと `src/` |
| クリティック | **Claude Code** | サンドボックス / `critic` ユーザー | `/srv/loop/critic/out` のみ | 仕様書、基本設計、詳細設計。受け入れ条件、コード、テストは読めない |
| 人間 | 保守ユーザー | サンドボックスとホスト | `/srv/loop/human/in` の仕様書とコメント | すべて。各段の出口で承認するか差し戻す |

**AI でないのはランナーだけ**。ランナーは決まった手順を実行するだけなので、
プログラムで書く。判断を AI に委ねると「まあ通ったことにする」が起こり得るが、
関門の値打ちは**判断しないこと**にあるため。

AI の3役は別々の uid で動き、資格情報も `/etc/loop/<役>.env` に分かれている。
各ファイルはその役の uid だけが読める。ランナーは sudo を持たず、
`/etc/sudoers.d/` にある役ごとの起動スクリプトへの例外でだけ他の uid を起こす。

サンドボックスは WSL2 のディストロ（§1-1）。保守ユーザー（sudo あり）も同じ
ディストロにいるが、ループの役には含まれない。

**プランナーは `docs/` と `ac/` を直接書けない。ソルバーは `plan/`、`docs/`、`ac/` を読めない。**
この2つが崩れると以下の全部が意味を失う。どちらもファイルシステムの権限で決まる。

サンドボックスの外側は**規律であって機構ではない**。Windows からは `wsl -u root` で
いつでも中の root になれるので、境界は片方向にしか立っていない ── 守っているのは
「サンドボックスから Windows 側へ手が伸びない」方向だけである（§1-4）。
人間の作業環境はサンドボックスの中身に手を入れない。

### 0-2. 非目標

- ソルバーの実装（Claude Code 等をサブプロセスとして呼ぶだけ）
- LLM API の抽象化（1種類決め打ちでよい）
- 並列実行（モジュールは依存の順に1つずつ）
- ディストロの作成・スナップショット操作（ホスト側の責務。§1-5）
- サンドボックスの生存管理（WSL2 はアイドルで落ちる。ホスト側 keepalive の責務。§1-6）
- GitHub への書き込み（プルリクエストはホストから出す。§2）

### 0-3. 設計原則

> **検知より剥奪。** ある関門を「違反を検知して止める」で実装できるときと
> 「そもそも実行不能にする」で実装できるときは、後者を選ぶ。
> 検知は二重化のためのトリップワイヤとしてのみ併置する。

BOOTSTRAP.md 1-7 の考え方を、テスト凍結と許可リストにも適用する。

## 1. 実行環境

### 1-1. サンドボックス

- **WSL2 ディストロ `Ubuntu-24.04`**（Ubuntu 24.04.1 LTS / `[boot] systemd=true`）
- `.wslconfig` で 6 プロセッサ / 8 GB RAM / swap 4 GB / `sparseVhd`
- リポジトリはディストロ内の **ext4 (VHDX) 上**。`/mnt/c` は使わない（理由は 1-4）
- `networkingMode=NAT`（**`mirrored` は使わない**。理由は 1-4）
  - 外部への egress（LLM API 用）
  - ホストからの SSH / git push/pull は、ディストロ内 sshd が **2222 で listen** し、
    `localhostForwarding=true` によって Windows の `127.0.0.1:2222` に出る

> VirtualBox から WSL2 に移した。ホストで Hyper-V が有効だと VirtualBox は NEM モードに
> 落ち、Linux ゲストが起動時に2回に1回ハングして数時間のループに使えなかった。
> 経緯と得失は `provision/README.md` §6。
>
> 「ソルバーが git 経路に触れられない」は**鍵を持たせないこと**で担保しており、
> ネットワーク構成には依存していない（`AllowUsers` にも載せない。§1-2）。

### 1-2. ユーザーとファイル所有

```text
maint : uid 1000. ディストロの既定ユーザー。sudo あり。保守と VS Code の接続先。
          ループの実行主体ではない。
runner  : uid 1001. リポジトリ全体を所有。sudo なし。SSH 鍵あり。
solver  : uid 1002. sudo なし。SSH 鍵なし。sshd の AllowUsers に載せない。
          他ユーザーの $HOME 参照不可（`maint` の home も。ここに人間の鍵と
          エージェント CLI の認証情報が入るため）。
```

リポジトリは **`/srv/loop/` に置く。どの home にも置かない。**
`/home/runner/project` にすると、solver が project に降りるために `/home/runner` に
通過権限が必要になり、home を 700 にできなくなるため。

```text
/srv/loop/
  repo.git/         bare。runner が push、ホストが引く
  project/          ループが回る作業ツリー
  brief/            runner → solver の唯一の受け渡し口（§5）
  planner/out/      runner が設計を写し、planner が書き直す（§3-3）
  critic/out/       critic が指摘を書く（§3-4）
  human/in/         人が仕様書とコメントを置く
  settings.json     走行の設定（§7-5。root 所有）
```

`/srv/loop/project` 配下の権限（`X` = モジュールの位相により変化）:

| パス | 所有 | モード | solver から |
|---|---|---|---|
| `project/`（ルート自体） | runner:solverw | **3775**（setgid + **スティッキー**） | 新規作成のみ。runner 所有物の削除・改名は**不可** |
| `.git/` | runner:runner | 700 | **不可**（読みも不要） |
| `plan/`（stage.json、ledger.jsonl、INTERFACE.json、CRITIQUE.json、FAILURE.md） | runner:runner | 700 | **不可** |
| `docs/`（設計仕様書） | runner:runner | 700 | **不可** |
| `ac/`（受け入れ条件） | runner:runner | 700 | **不可** |
| `.runner/`（下流の計画、凍結マニフェスト、確定した契約） | runner:runner | 700 | **不可**（何を照合しているか見せない） |
| `tests/`（柵のテストの場所） | runner:solverw | `X`: 2775 → **555** | TEST_WRITE 中のみ書、FREEZE 以降 読のみ |
| `src/`（柵のコードの場所） | runner:solverw | 2775 | 書（§4-4 の経路チェックあり） |
| `conftest.py`, `pytest.ini`, `pyproject.toml` | runner:runner | 644 | 読のみ（常時。**スティッキー依存** ── 下記） |
| `.venv/` | runner:runner | 755 | 読・実行のみ、**書不可** |
| `/srv/loop/brief/` | runner:solverw | 750 | 読のみ |

柵の2つのディレクトリの場所はプロジェクトごとに決まる。`/srv/loop/layout.json`（root 所有。
`loop-project.sh` が今のプロジェクトのものへ向けるリンク）の `src` と `tests` で、無ければ
`src/` と `tests/`。Unity のプロジェクトはコードを `Assets/` の下に置く。この節と以降で
`src/` と `tests/` と書くのは、柵のその2つの場所のこと。ランナーは起動時に一度だけ読み、
壊れた値なら既定に戻らずに止まる。既定に戻ると、柵が黙って別の場所に開くからだ。

**ルートが書ける理由と、スティッキーが要る理由**（2026-08-18 実測）。Codex の
`apply_patch` はワークスペースのルートを経由して書くため、ルートが読み取り専用だと
`src/` に権限があっても全ての編集が失敗する（しかも失敗は対象ファイル名で報告され、
原因から遠い）。しかし**書けるだけでは穴になる** ── unlink と rename はファイルではなく
**親ディレクトリ**の書き込み権で決まるので、`conftest.py` を改変できない solver でも
削除して自作に差し替えられてしまう。テストの収集方法は FREEZE が守るべきものの中心なので、
これは凍結の実質的な無効化にあたる。スティッキービットは「削除・改名は所有者のみ」に
制限するのでこれを塞ぐ。solver は**新規作成だけできて runner の持ち物には触れない**。
`40-perms.sh` が両方を assert する（作れること／消せないこと）。

残る経路が1つある。solver はルートに**新規ファイルを置ける**ので、`AGENTS.md` のような
エージェントが自動で読む文書を仕込める。`--ignore-rules` で `.rules` は閉じているが
`AGENTS.md` は別。**ランナーはモジュールの開始前にルート直下のファイル一覧を許可リストと
照合すること**（`--ephemeral` はセッションの永続化を止めるだけで、ファイル経由の持ち越しは
止めない）。

**solver は `plan/`、`docs/`、`ac/` に一切アクセスしない**。ソルバーが受け取るのは
runner が `brief/` に組み立てたその1モジュール分のブリーフだけ（§5）。
これで「設計の全体や受け入れ条件を覗く」経路が権限レベルで存在しなくなる。

planner は `src/` を ACL（`user:planner:r-x`、default 付き）で読めるが、書けない。根から
`src/` までの道には `--x` だけを付け、`tests/` には何も付けない。critic は `src/` にも届かない。

ソルバーは `solver` グループ経由で `src/` にのみ書き込む。
テスト凍結（1-3）は **FREEZE 位相で `chown runner:runner tests/ && chmod -R a-w tests/`**
によって実装する。ハッシュ照合は二重化のトリップワイヤであって主機構ではない。

### 1-3. sudo を渡さない理由はサンドボックスでは変わる

隔離が効いていれば（§1-4）、仮にディストロ内で root を取られても Windows 側への
被害はほぼない。したがって `solver` を sudo なしにする目的は**安全性ではなく再現性**である。

`apt install` や `pip install` が通ってしまうと、ブリーフが伝えた環境と
実際の環境が乖離し、green が再現不能になる。**環境の変更は必ずモジュールの停止として
表面化させる**（= 詰まったので勝手に入れた、を検出可能にする）ことが目的。

**ただし、この目的は egress を塞がなくても既に達成されている**（2026-08-18 実測、
ネットワーク全開の状態で）。

| 試みたこと | 結果 | 効いている機構 |
|---|---|---|
| `.venv/bin/pip install requests` | Permission denied | `.venv` が runner 所有・`go-w` |
| `pip install --user requests` | externally-managed-environment | PEP 668 |
| `--user` で入れたものを `.venv/bin/python` から import | 見えない | venv は user site を無視する |
| `apt-get install` | dpkg lock: are you root? | sudo なし |

3つ目が要になっている。**テストは必ず `.venv/bin/pytest` で走らせること** ── ここを
素の `python3` に変えると user site が復活し、この防御だけが崩れる。

したがって egress 制限が買うのは環境凍結ではなく、**外部からの持ち込みと持ち出し**
（ソルバーが web から指示や実装を拾う／プロジェクトを外に出す）である。優先度は
そちらの脅威をどう見るかで決まり、環境凍結の前提条件ではない。

以下は持ち込み・持ち出しを塞ぐ場合の構成:

```bash
# 既定 DROP、プロキシ経由のみ許可（uid ベース）
iptables -A OUTPUT -m owner --uid-owner solver -o lo -j ACCEPT
iptables -A OUTPUT -m owner --uid-owner solver -d <proxy> -p tcp --dport 3128 -j ACCEPT
iptables -A OUTPUT -m owner --uid-owner solver -j DROP
```

ローカルの許可ドメインのみ通すフォワードプロキシ（tinyproxy 等）を `runner` で動かし、
許可先は **LLM API のドメインのみ**。PyPI も apt も通らない。

> v1 簡易版: プロキシを立てず、`--uid-owner solver` で DNS(53) と API の IP のみ ACCEPT。
> IP 変動で壊れるので、壊れたら上の構成に上げる。
>
> **この簡易版は現状では勧められない**（2026-08-18 実測）。ソルバーの実際の宛先は
> `chatgpt.com` の1つだけだが、それは Cloudflare の後ろにあり、いま2アドレスに解決される。
> IP 固定は黙って陳腐化する。しかも WSL2 では VM が頻繁に止まるので規則の永続化が要り、
> **永続化した固定 IP は時限爆弾になる**（ローテーション後、原因の分かりにくい停止として出る）。
> 塞ぐならプロキシ構成で作ること。
> WSL2 のイメージには iptables が入っていないので `60-egress.sh` が自分で入れる。
> また VM がアイドルで落ちるたびにルールが消えるため、`iptables-persistent` は必須。

### 1-4. 隔離は既定では成立していない

WSL2 は VirtualBox と違い、**既定でホストと地続き**である。3つを明示的に切って初めて
サンドボックスになる。

| 既定の挙動 | 切り方 | 切らないと |
|---|---|---|
| Windows ドライブを `/mnt` にマウント | `/etc/wsl.conf` `[automount] enabled=false` | solver が Windows のファイルを読み書きできる |
| `.exe` を起動できる（interop） | `[interop] enabled=false` + `appendWindowsPath=false` | solver が `powershell.exe` を呼べる |
| WSLg（GUI/音声/クリップボード） | `.wslconfig` `guiApplications=false` | `/mnt/wslg` の誰でも読めるソケット経由で Windows 側のコンポジタと PulseAudio に届く |
| `mirrored` なら Windows の localhost に到達 | `.wslconfig` `networkingMode=NAT` | Windows 側で listen しているサービスに触れる |

これらは **root に対する防御ではない**。ディストロ内の root は
`mount -t drvfs C: /somewhere` でいつでも Windows ドライブを持ち込める（実測）。
効いているのは「`solver` は sudo を持たないのでマウントできない」という一点で、
つまり隔離の実質は §1-2 の権限モデルと同じ土台に乗っている。
interop の binfmt ハンドラも `enabled=false` でも登録されたまま残るので、
**ハンドラの有無は証拠にならない**（`provision/README.md` §3-9）。

`/mnt/c` を使わない理由はもう一つある。DrvFs は所有者とモードビットを正しく持てないため、
**`tests/` を solver から書き込み不可にする（1-2 の主機構）が成立しない。**
リポジトリはディストロのネイティブ ext4 上に置く。

これらは「設定を書いた」では確認にならない。`/etc/wsl.conf` と `.wslconfig` の変更は
`wsl --terminate` では反映されず `wsl --shutdown` が必要で、書いたまま効いていない状態が
普通に起きる。だから `provision/05-isolation.sh` が**現在の状態**に対して assert する
（マウントテーブル、`/mnt/c` の中身、PATH、`/mnt/wslg` の有無、systemd、`loopback0`）。

ホストとの受け渡しは git 経由（§2）。ホストから編集する場合は VS Code Remote-SSH で
`maint` に繋ぐ（`loop-dev` コマンド）。ファイルを送り込むときは `/mnt/c` が無いので scp。

### 1-5. スナップショットと git の役割分担

| 壊れたもの | 戻し方 |
|---|---|
| コード（緑のモジュールを捨てる） | **git**。モジュール単位のコミットとタグ |
| 環境（何かが入った・壊れた） | **`wsl --export` / `--import`**。ホスト側から |

ランナーはスナップショットを操作しない。
プロビジョニング直後に `wsl --export` を1本取っておくこと。

VBox スナップショットに比べて差分が取れず数 GB になるので、頻繁には取れない。
危険な無人実行の前に1本、が現実的な運用。`--export` は停止状態が必要なので
`wsl --shutdown` を伴い、**その後 keepalive タスクの再起動が必要**（§1-6）。

### 1-6. サンドボックスの寿命 ── 無人実行はできない

WSL2 の VM は **約60秒アイドルすると VM ごと停止する**。しかもアイドル判定は
`wsl.exe` クライアントセッションだけを数え、**SSH のトラフィックは数えない**。
つまり VS Code Remote-SSH で接続中でも、デタッチしたループを走らせていても落ちる。
`vmIdleTimeout` は効かない（実測済み）。

これを抑えているのはホスト側の keepalive スケジュールタスクだけで、それは
ログオンセッションに紐づく。したがって:

- **ログオフを跨いでループを回すことはできない。** `runner run --all` は人が
  ログオンしている間だけ走る
- 途中で VM が落ちる可能性が常にあるので、**台帳（§7-1）からの再開が飾りではなく
  必須機能になる**。位相の途中で死んだ場合に安全側（当該モジュールをやり直す）に
  倒れること
- 無人で数時間回す必要が出たら Hyper-V に移す。ディストロ内の構成はそのまま移せる

詳細は `provision/README.md` §3-1 と §5。

## 2. ホストとの境界

```text
ホスト (Windows)                    WSL2 / Ubuntu-24.04
─────────────────                   ───────────────────
人間
  └ loop go / approve / reject / reopen（SSH）
                                    /srv/loop/human/in ── 仕様書、コメント
                                    │
                                    ▼
                          /srv/loop/project ──── ランナーと3役
                                    │  段のコマンドと GREEN のたびに push
                                    ▼
  写し        ◀──pull────  /srv/loop/repo.git (bare, runner 所有)
  （ssh 127.0.0.1:2222, runner）
     │
     └ 下書きのプルリクエスト（ホストから。箱は GitHub に触れない）
```

- bare リポジトリはディストロ内に置き、ホストからは SSH で引く（`runner` 鍵）
- **`solver` は SSH 鍵を持たず、`AllowUsers` にも載っていないので、この経路に触れられない**
- `runner` 鍵は保守用（`maint`）の鍵とは別に作る。前者は git 経路専用
- 人間は `docs/` にも `plan/` にも直接書かない。仕様書とコメントは `human/in` に置き、
  ランナーが取り込む（§3-2）
- コミットするのは `docs/`、`plan/` の段と台帳と検査の結果、コードだけ。`ac/` とテストは
  `.gitignore` で外す。受け入れ条件は runner だけが読み、テストは作業ツリーに残して
  VERIFY の回帰検知に使う
- プルリクエストはホストが写しの HEAD から出す。ランナーは GitHub に書き込まない

## 3. 段

### 3-1. 段とせき

流れは3段と最終確認に分ける。各段の出口でせき止め、人間が満足するまでその段の中で回す。

| 段 | 成果物 | 回す者 | 出口 |
|---|---|---|---|
| `upstream`（上流） | `docs/basic/` の基本設計仕様書 | プランナー ⇄ 人間 | `basic approve` |
| `midstream`（中段） | `docs/modules/` の詳細設計仕様書と `ac/` の受け入れ条件 | プランナー → クリティック → 人間 | `modules approve` |
| `downstream`（下流） | 実装 | ソルバー ⇄ VERIFY | 全モジュールが緑で `review` へ。止まれば `midstream` へ |
| `review`（最終確認） | 下書きのプルリクエスト | 人間 | 承認はホストで行う。直すなら `reopen` で `midstream` へ |

段は `plan/stage.json` に置く。

| キー | 意味 |
|---|---|
| `stage` | 上の4つのどれか。無ければ始まっていない |
| `language`、`framework` | コードの言語と持ち込む先。最初の `basic draft` で決まり、以後変わらない |
| `open` | 中段でプランナーが書き直してよいモジュール。`null` なら全部。`[]` は下流で止まった後で、人が直すモジュールを選ぶのを待っている |
| `critiqued` | クリティックが読んだ設計のハッシュ。今の設計のハッシュと一致しなければ承認できない |

各コマンドは自分の段でしか動かない（`in_stage`）。段が違えば何もせずに 1 で終わる。

### 3-2. 段のコマンド

| コマンド | 段 | すること |
|---|---|---|
| `spec import` | どこでも | `human/in/spec/` のファイルを `docs/spec/` に写してコミットする。最初の取り込みで `upstream` を始める |
| `basic draft [--language <言語>] [--framework <持ち込む先>]` | `upstream` | プランナーに基本設計を書かせる。言語は最初の1回で必須 |
| `basic approve` | `upstream` | 基本設計の形（§6-2）を確かめ、`midstream` へ移す |
| `modules draft` | `midstream` | プランナーに詳細設計と受け入れ条件を書かせ、続けて `modules critique` を流す。`open` が `[]` なら拒む |
| `modules critique` | `midstream` | クリティックに今の詳細設計を1回読ませる |
| `modules approve` | `midstream` | 形とインターフェースの検査（§6）を通り、クリティックが今の設計を読んでいれば、下流の計画を作って `downstream` へ移す |
| `reopen <モジュール>...` | `midstream`、`downstream`、`review` | 作業ツリーを最後のコミットに戻し、`midstream` に戻す。`open` を選んだモジュールにする |
| `run <モジュール>`、`run --all` | `downstream` | モジュールを実装する（§3-5） |

人のコメントは `human/in/COMMENT.md` に置く。`basic draft` と `modules draft` はそれを
ブリーフの「What the human said about the last version」に載せ、書いた設計が検査を
通ったら消す。

`modules approve` は、緑のモジュールのうち設計のハッシュ（詳細設計と受け入れ条件の
ハッシュ）が緑になったときと変わったものを、流し直す対象にする。そのテスト、凍結の
マニフェスト、確定した契約を消し、台帳に `REOPEN` を書く。設計が変わらなかった緑の
モジュールは走らせ直さない。

### 3-3. プランナーの経路

プランナーは `planner/out/` の下の `basic/`、`modules/`、`ac/` に書く。ランナーは呼ぶ前に
out/ を空にし、今の文書をそこへ写して置く。どの部分を置くかが、プランナーの書ける範囲だ。

| コマンド | 置く部分 |
|---|---|
| `basic draft` | `basic/` |
| `modules draft` | `modules/`、`ac/` |

呼び出しの後、ランナーは次を順に行う。

1. 置かなかった部分、拡張子の違うファイル、シンボリックリンクを読まずに消す（`prune_planner_out`）
2. 書かれたものを検査する。`basic draft` は §6-2、`modules draft` は §6-3 から §6-5
3. 通れば `docs/` と `ac/` に戻してコミットする。落ちれば、消したものと検査の判定を
   そのまま次のブリーフに載せて呼び直す。上限は `limits.revisions` 回（既定 3）

差し戻し（`open` がモジュールの一覧）のときは、指定外のモジュールの詳細設計と受け入れ
条件が1字でも変わっていれば拒む。モジュールの追加と削除も拒む。基本設計は中段では
置かないので変えられない。

プランナーは `src/` を ACL で読めるが、書けない（`40-perms.sh`）。テストには届かない。
ブリーフは既存のコードの宣言を引数と戻り値の型を外した短い形で渡す。requires の行は
名前で突き合わせ、ソルバーには HEAD の署名を渡すので、プランナーに型は要らない。

### 3-4. クリティック

クリティックは中段で詳細設計を1回だけ読む。ブリーフに載るのは仕様書、基本設計、すべての
詳細設計だけで、受け入れ条件もコードもテストも載せない。

見るものは3つ。

- **Coverage** — すべてのモジュールが設計どおりに動いたら、仕様書は満たされるか
- **Reach** — 入口（`"entry": true`）から、使う人が届く振る舞いはどれか。どこからも
  呼ばれない振る舞い、誰も書かないのに読まれるものは無いか
- **Boundaries** — 契約が渡さないものを要るモジュール、互いに相手の仕事だと思っている
  2つのモジュールは無いか

答えは `critic/out/FINDINGS.json` の1つだけで、`{"findings": [...]}` の形。ファイルが無い、
読めない、`findings` の一覧が無い答えは、批評が無かったものとして止まる。空の一覧は
「何も見つからなかった」という答えだ。

指摘はプランナーに戻さない。`plan/CRITIQUE.json` に設計のハッシュと一緒に書いてコミットし、
写しを `human/in/CRITIQUE.json` に置く。プランナーに書き直させるかは人が決め、コメントで
伝える。

### 3-5. モジュールの位相

下流では、1モジュールが次の位相を通る。位相は `plan/ledger.jsonl` に記録する。

```text
 PLAN_LOAD
     │  .runner/tasks.json からモジュールを読む。作業ツリーが汚れていれば止まる。
     │  緑のモジュールが無ければ、tests/ の既存のスイートを走らせる。
     │  落ち・エラー・スキップがあれば、設計を差し戻さずに止まる
     ▼
 TEST_WRITE            ソルバー呼び出し（単体テストと統合テストを書かせる）
     │                 書込許可: files_test のみ
     ▼
 STUB                  ランナーが契約からスタブを書く（§5-1）
     │                 書込許可: files_write のみ
     ▼
 RED_GATE ────────────▶ 不合格 → 中段へ戻す（§7-2）
     │  §4-1
     ▼
 FREEZE                tests/ を読み取り専用化 + マニフェスト採取
     │  §4-3
     ▼
 IMPL ◀───┐            ソルバー呼び出し（実装）
     │     │           書込許可: files_write のみ
     ▼     │
 VERIFY ───┘ 不合格かつ試行が残っている
     │  §4-4
     ▼
 GREEN                 コミット + タグ + 契約を確定
```

**位相ごとにソルバーの呼び出しを分ける**のは、テストを書く文脈と実装を書く文脈を
混ぜないため。受け入れ条件は TEST_WRITE のブリーフにだけ載せる。

統合テストは、モジュールを依存先の実物と一緒に動かすテストだ。依存先は依存の順で
先に緑になっているので、統合テストは代役を使わずに書ける。VERIFY はスイート全体を
走らせるので、緑のモジュールどうしの統合も毎回確かめる。

## 4. 関門の判定条件

判定はすべて機械可読な事実に基づく。下流に人間の判断は入らない。

テスト実行は常に:

```bash
.venv/bin/pytest <files_test...> \
  --junitxml=.runner/report.xml \
  -p no:cacheprovider \
  --strict-markers -q
```

判定は **exit code ではなく junit XML** を読んで行う。

**`<testsuite>` は全部足す。最初の1つではない**（2026-09-02 修正）。pytest は1回の実行に
`<testsuite>` を1つしか書かないので、**「最初の suite」と「レポート全体」は同じもので、
区別する理由が存在しなかった** ── `root.find("testsuite")` は正しく見えていた。
vitest は**テストファイルごとに1つ**書く。VERIFY は `tests/` 全体を渡すので、
複数ファイルなら1ファイル分しか数えないことになる。実測（2ファイル・3テスト・1失敗）:

```text
古い読み方 : tests 1  failures 1     ← 失敗した1ファイルだけ
新しい読み方: tests 3  failures 1     ← 正しい
```

しかも vitest の suite 順は**完了順**で固定されない。上の実行はたまたま失敗ファイルが
先だったが、逆なら **2テスト・0失敗** を返す ── **VERIFY が落ちている suite を緑と呼ぶ。**
非決定的に偽陽性を出す関門であり、2言語目を入れるまで**そこに在ったことすら分からなかった**。

### 4-1. RED_GATE（BOOTSTRAP 1-2 の実装）

以下を**すべて**満たすときのみ合格:

| # | 条件 | 防ぐもの |
|---|---|---|
| R1 | 収集されたテスト数 == `expected_tests`（受け入れ条件の数） | テスト0件 / 水増し / 不足 |
| R2 | `<error>` 要素が **0 件** | 収集エラー・ImportError を red と誤認 |
| R3 | `skipped` が **0 件** | 全 skip の exit 0 |
| R4 | 全テストが `<failure>` を持つ | 一部が既に通っている＝テストが自明 |
| R5 | 全 `<failure>` の `type` が `AssertionError` または `Failed` のみ | 下記 |

**R5 が本体。** `ImportError` / `ModuleNotFoundError` / `AttributeError` / `TypeError` /
`NameError` での失敗は **red と認めない**。

これにより、赤の意味が「まだ実装がない」から
**「呼び出しは全部成立していて、値だけが違う」**に変わる。
副次的に、実装を1行も書く前に**契約のシグネチャが正しいことが検証される**。

**R4 は1件でも通れば止まる**。他に落ちる条件があっても救われない ── 通ったテストは
「落ちうること」を一度も示していないので、そのあと緑になっても意味が無いという理屈がそのまま
効く。受け入れ条件がこれを踏む道は2つあり、**両方とも中段でしか直せない**:

1. 期待値がスタブでも出せる値（空文字・0・空リスト・引数そのまま）
2. 期待結果を**コード自身が生んだ2つの値の比較**として書く。
   `advance(p.state, catalog, 0.0) == p.state` がこれで、両辺とも同じ番兵になり通ってしまう
   （run 4 S1 で停止）

**R4 はスタブの返り値に依存する**（2026-08-18 実測）。`normalize` の実装で、スタブが
`""` を返したところ「空文字入力→空文字出力」の境界条件2件が**正解してしまい** R4 で停止した。
別の実行でスタブが `"__stub__"` を返したときは全件落ちた。つまり R4 の成否は、
スタブが**どの正解とも一致しない値**を返すかどうかで決まる。したがって STUB のブリーフは
「型が合っていて間違った値」では不十分で、**目立つ番兵値**を明示的に要求しなければならない
（§5-1）。空・ゼロ・既定値・引数そのままは、いずれもどこかの入力に対する正解なので禁止する。

不合格時の扱い:
- テストファイルがコンパイルできない → コンパイラの出力を載せて TEST_WRITE をやり直させる
  （`test_writes` 上限 3）
- C# で、ランナーが書いたスタブに対する R5 違反が `NullReferenceException` と `IndexOutOfRangeException`
  だけ → 落ちたテストの名前と例外を載せて TEST_WRITE をやり直させる（`test_writes` 上限 3）。
  最後の試行でも落ちれば、ファイルを残したまま R5 で止まる
- R5 違反で止まるとき、`FAILURE.md` の詳細に落ちたテストの名前と例外を載せる
- R1 違反 → テストと条件の数の不一致。**中段へ戻す**（§7-2）
- R4 違反（スタブが通ってしまった）→ 条件が自明。**中段へ戻す**

### 4-2. 受け入れ条件からテストへの翻訳

受け入れ条件からテストコードへの翻訳はソルバーが単独で行う。BOOTSTRAP 1-1 の漏れ口は
ここに残る。人間は条件を中段で読み、`then` が具体的な値を述べることを §6-4 が機械で確かめる。

### 4-3. FREEZE（BOOTSTRAP 1-3 の実装）

**主機構（剥奪）:**
```bash
chown -R runner:runner tests/
chmod -R a-w tests/
chmod a-w conftest.py pytest.ini pyproject.toml   # 存在するもの
```

**トリップワイヤ（検知）** — `.runner/freeze/<id>.json` に記録:

| 記録項目 | 検出できる細工 |
|---|---|
| `files_test` 各ファイルの sha256 | 直接の書き換え |
| 全階層の `conftest.py` の sha256 と**存在しないパスの一覧** | conftest の新規追加による fixture 差し替え |
| `pytest.ini` / `pyproject.toml` / `tox.ini` / `setup.cfg` の sha256 | `addopts`、収集ルート、マーカーの改変 |
| `--collect-only -q` のテスト ID 全集合の sha256 | 件数を保ったままの入れ替え |
| `expected_tests` | 削除 |
| `pip freeze` の sha256 | 環境の変更 |

「存在しないパスの一覧」は重要。ハッシュは**あるファイル**しか守らないので、
`tests/conftest.py` や リポジトリ直下の `sitecustomize.py` の**新規作成**が素通りする。

### 4-4. VERIFY（IMPL の各試行後）

順に判定し、最初に落ちた時点で打ち切る:

1. **凍結整合** — `.runner/freeze/<id>.json` を再照合。1つでも不一致 → **即停止**（リトライしない。テストに手を入れた事実は試行回数の問題ではない）
2. **経路許可** — `git status --porcelain --untracked-files=all` の全パスが `files_write` に含まれるか。含まれないパスが1つでもあれば → 即停止
3. **テスト結果** — **`tests/` 全体**を走らせ、`<error>` 0、`skipped` 0、`<failure>` 0
4. 3 が不合格 → `attempt += 1`。試行予定（§4-4-1）が残っていれば IMPL に戻る

2 は権限だけでは足りない部分（`src/` 内で宣言外のファイルを作る）を埋めるための検知。
`.git/`、`tests/`、`plan/`、`docs/`、`ac/` は権限で既に守られている。

**3 で全スイートを走らせるのは、モジュールの完了が2つの半分でできているから。**
「このモジュールのテストが通る」（FAIL_TO_PASS）と「通っていたテストが1つも落ちない」
（PASS_TO_PASS）。後者が、緑のモジュールどうしの統合テストでもある。

**skip は緑ではない。** 上の 3 は最初からそう書いてあったが、**実装は `skipped` を
見ていなかった**（`TestRun.green` が `tests > 0 and failures == 0 and errors == 0`
だけを見ていた。2026-08-21 修正）。RED_GATE は R3 で skip を拒否するのに VERIFY は
しない、という非対称は PASS_TO_PASS の穴になる ── 後続の実装が動的な skip 条件
（`skipif` や `importorskip`）を成立させると、以前は通っていたテストが**走らないまま
素通り**し、黙って縮んだスイートでモジュールが緑になる。判定に入れるだけでなく、
**台帳の VERIFY レコードに `skipped` を残す**。緑は事後に台帳だけで証明できる必要があり、
「failure が 0 件」はテストが走ったことの証明にならないため。
skip で止まった場合はソルバーへのフィードバックに**走らなかったテストを名指しする**
（pytest 自身はその実行を成功と呼ぶので、出力を渡すだけでは手掛かりが無い）。

**RED_GATE は逆に、そのモジュールのテストだけを走らせる**（R1 の収集数が
`expected_tests` と一致することに意味を持たせるため）。関門ごとに対象が違うのは意図的で、
それぞれの仕事が違う。

前のモジュールのテストが落ちた場合、その事実を**ソルバーへのフィードバックに明示する**。
`tests/` は凍結されていて編集できないので、直せるのは実装だけであり、
それを言わないと直しようのない指示になる。試行を使い切った場合は
`FAILURE.md` の関わったモジュールに**壊した相手を名指しする** ── 「まだ実装できていない」と
「前のモジュールを壊さずには実装できない」は別の問題で、後者は設計どうしの
矛盾の可能性があり、ソルバーが決めることではないため。

### 4-4-1. 試行の始め方と、ソルバーの段

**1モジュールの試行予定は「試行回数 × ソルバー段」で決まる。** ランナーは
`attempt_schedule(step)` で「何回目をどのバックエンドが走るか」の一覧を先に作り、
それが尽きるまで IMPL ⇄ VERIFY を回す。

**試行回数** — `max_attempts`（モジュール単位。既定 3）。`settings.json` の
`"limits": {"attempts": n}` で**全モジュールを一括で上書き**できる（0 は「モジュールの値」）。
適切な回数は**誰が試行の代金を払うか**で決まる。枠を消費するソルバーなら 3 が正しく、
ローカルのソルバーなら試行の原価は実時間だけなので、10回でも中段への差し戻し1回が買う
**人の手1回より安い**。

**始め方** — `settings.json` の `"policy": {"retry": "repair" | "resample"}`。

| | 作業ツリー | 直前の失敗の伝達 |
|---|---|---|
| `repair`（既定） | 失敗したまま引き継ぐ | 渡す |
| `resample` | HEAD に戻す | 渡さない（RED_GATE の失敗のみ） |

`resample` は「失敗した実装はソルバーに渡さない。壊れた方針への固着を避けるため」を
試行の粒度で採る方針。自分の失敗を読んで直せるソルバーには `repair` が正しく、
そうでないソルバーでは損傷が累積し、後の試行ほど悪い木から始まる。そしてランナーは
**厳密な検証器**なので、同じ予算を「N回の独立した抽選」に使う選択肢が成立する ──
誤魔化せない関門に対する N 回の抽選は、弱いソルバーでは修復より強い。

巻き戻しは `git reset --hard` **ではない**。このモジュールのテストは書かれているが
コミットされない（`.gitignore` で外してある）ので、reset は満たそうとしている当の
テストを消す。戻すのは `files_write` のパスだけで、それは経路許可（4-4 の 2）が
「変わったのはここだけ」と既に確認した集合と同一。台帳に `DISCARD` を残す。

**時間切れ** — IMPL でソルバーが `timeouts.solver` 以内に終わらなかった試行（solver-run の
終了コード 124）は、試行1回分の失敗として数え、次の試行へ進む。書きかけの作業は
`repair` でも捨てる。途中で止まったファイルは修理の土台にならないからだ。凍結の
照合と経路許可は成功した試行と同じく通し、破っていれば今までどおり止める。
台帳に `SOLVER_TIMEOUT` を残し、次の試行のブリーフに時間切れだったことを伝える。
試行を使い切ったときの理由には、何回が時間切れだったかを書く。TEST_WRITE と STUB の
時間切れ、および runner 側の上限（`BACKSTOP_MARGIN`）に当たった場合は、モジュールを止める。
後者はソルバーのプロセスがまだ生きているかもしれないからだ。

**ソルバー段** — `settings.json` の `"solver_tiers"`。**既定は `["claude"]`**（§7-5）で、
段は1つ。2段にするときは `"solver_tiers": ["local", "claude"]` のように書く。
先頭の段が**試行を使い切ってから**、次の段がそのモジュールを初めて見る。交互ではない
── 早すぎる引き渡しは、安い側がまだ試し終えていない仕事に高い側を使う。段が変わる回は
作業ツリーを捨てるが、**失敗の文面は渡す**（引き渡しは「前任の書きかけを継ぐこと」では
ないが、既に分かっていることを捨てる理由も無い）。

段を2つ置く理由は費用ではなく**費用の比較**にある。試行を使い切った先にあるのは
中段への差し戻しで、それは**人の手**を1回使う。2段目のソルバーは追加の
出費ではなく、次に起きる2つのことのうち安い方。

ランナーが渡すのは**バックエンドの名前だけで、コマンドではない**。名前から実体への
対応は root 所有の `bin/solver-run` が持ち（`/srv/loop/bin/solver-<name>`、root 所有
0755、引数は `<brief> <seconds>`）、ランナーはバックエンドを**追加できず**、sudo を
持つ人間が既に置いたものを指名できるだけ。名前は `[a-z0-9]+` で検査する ── パスに
埋め込まれるため。走ったバックエンド名は台帳の `ADOPT` / `VERIFY` に
残る。どの段が緑を出したのかは、事後に台帳だけで答えられる必要がある。

| 名前 | 実体 | コマンドの実行 | 資格情報 |
|---|---|---|---|
| `claude` | `solver-claude`（Claude Code。`Read` `Write` `Edit` のみ） | できない | `/etc/loop/solver.env` |
| `local` | `solver-local`（ローカルの llama.cpp サーバ。`docs/LOCAL_SOLVER.md`） | できない | 無い |
| `codex` | `solver-run` 自身が起動する Codex CLI | サンドボックスの中でできる | `/home/solver/.codex` |

コマンドを実行できないバックエンドだけで段を組むと、ランナーはプランナーとソルバーの
ブリーフに「ソルバーはコマンドを実行できない」と書き足す。プランナーが「このコマンドで
確かめてから終えよ」と設計に書き、ソルバーが試行をそれに使うのを防ぐ。

### 4-5. GREEN

```bash
ledger GREEN（設計のハッシュを添える）
git add -A
git commit -m "<id>: green"
git tag -f module-<id の / を -- に替えたもの>
```

`GREEN` は実装と同じコミットに含める。次のモジュールのコミットに持ち越すと、最後のモジュールには
持ち越し先がなく、bare リポジトリとホスト側ミラーの台帳が常に1つ遅れるため。テストは
`.gitignore` で外してあるので、`git add -A` はコードと台帳だけを入れる。

`contracts.provides` を `.runner/contracts/<id>.json` に確定保存。以降のモジュールは
**この確定済み contracts のみ**を参照する。

続けて `origin`（`/srv/loop/repo.git`）へ push する（`publish()`。段のコマンドのコミットの後にも
同じことをする）。狙いは、緑になったモジュールを `reset` / `clean` の射程から外すこと。

**push の失敗はモジュールを落とさない。** 緑の根拠はテストが通ったことであって、
ミラーが受理したことではない。台帳に `PUBLISH_FAILED` を残して先へ進む。
ブランチは `--force` を付けずに押す ── ランナーは履歴を書き換えないので、
non-fast-forward は**この仕様が知らない何かが起きた印**であり、上書きは誤り。
タグだけは `tag -f` で動きうるので force で押す。

`repo.git` は同じ VHDX の中にあるので、**これはバックアップではない**。
ディスクごと失う場合に備える複製はホストが SSH で引く（`host/loop-pull.cmd`）。
**押すのではなく引く**のは、外に届く認証情報をサンドボックス内に置かないため。

最後のモジュールの後は `ALL_GREEN` と設計のハッシュを台帳に書き、段を `review` に移して
完了コミットを作り、もう一度 publish する。これがホストの最終確認を始める客観的事実になる。
同じ計画ハッシュの `ALL_GREEN` が**コミット済みなら**完了コミットを重ねない。判定は台帳
ファイルではなく `git show HEAD:plan/ledger.jsonl` を読む ── 台帳に書いた直後にコミットが
失敗した場合、「ファイルに書いてあるから済んだ」と見なすと**二度と publish されず**、
この仕組みが直したはずの症状（ミラーが完了を映さない）に戻るため。記録がファイルにだけ
ある場合は、追記せずコミットだけをやり直す。

### 4-6. ランナー自身のテスト

`runner/tests/`。**標準ライブラリだけ**で書き、題材側の venv には依存しない
（venv はプロジェクトのものなので、そこに engine のテストをぶら下げない）。

```bash
python3 -m unittest discover -s runner/tests
```

中心は `parse_junit` ── 関門の算術が実際に住んでいる場所で、RED_GATE も VERIFY も

どちらも「読めば分かる」種類の欠陥だった。

## 5. ブリーフの組み立て（BOOTSTRAP 1-5 の実装）

ソルバーは `docs/` も `ac/` も読めない。ランナーが要る部分だけを抜き出してブリーフに入れる。
**設計の全体は渡さない。**

| 渡すもの | 出どころ |
|---|---|
| システムの目的 | 基本設計仕様書の `## 概要` の節 |
| コードの置き方 | 言語と持ち込む先の `layout_note` |
| 自分のモジュールの設計 | 自分の詳細設計仕様書（契約のブロックを除く） |
| 依存先の振る舞い | 依存先の詳細設計仕様書の `## 振る舞い` の節 |
| 依存先の署名 | 緑になったときに確定した契約（`.runner/contracts/<id>.json`）と、requires が名指しした既存のコードの HEAD の宣言 |
| 自分が提供する署名 | 自分の契約の provides の行 |

位相ごとには次のとおり。

```text
[TEST_WRITE]
  上の背景、依存先の署名、自分の署名
  受け入れ条件（ac/<id>.json の criteria）
  書くテストのファイル（files_test）

[STUB]
  ソルバーは呼ばない。ランナーが書く（§5-1）

[IMPL]
  上の背景、依存先の署名、自分の署名
  goal
  凍結したテストの内容（読み取り専用）
  今のファイルと、既存のファイルなら HEAD の中身
  直近の失敗（このモジュールの前の試行のみ）
  書けるファイル（files_write）
  ※ 受け入れ条件は渡さない
```

TEST_WRITE と IMPL のブリーフは同じ本文（`solver_material`）で始める。先頭がそろって
いれば、後の呼び出しはこの部分をプロンプトキャッシュから読む。

### 5-1. STUB はソルバーに書かせない

**ランナーが組み立てる。** スタブの仕事は「形は正しく、値は全部間違っている」の一つだけで、
そこに判断は要らない。`contracts.provides` が署名と型の中身を持ち、置き場はモジュールの
パスが決める。§6-5 の「形」がそれを保証する。

8回の run はソルバーに書かせていた。run 8 の S1 は**正解を返すスタブ**で4回止まっている ──
`return false`、そして温度を下げたあとは
`return {resource: 0, generators: {}, lastUpdate: 0}`（createGame の正しい初期状態）。
ブリーフは「空・ゼロ・既定値を返すな」と明示している。**届いて、読めて、無視された。**

**モデルが無視できる指示より、届かない規則のほうが強い。** `sudo` を監視せず取り上げるのと
同じ判断。

- **boolean だけが例外。** どの boolean も何かの正解なので「正しい型の間違った値」が
  存在しない。そこだけ異物（`"__stub__" as unknown as boolean`）を返す。数値・文字列・
  配列・オブジェクトは自分の番兵を持つ（文字列にすると `TypeError` になり R5 が弾く）
- **辞書型には受け入れ条件が引用しているキーを入れる。** `CATALOG.cursor.rate` は
  cursor が無ければ比較の前に落ちて R5 になる。契約はキーを言えない
  （`Record<string, GeneratorDef>` は型であって名簿ではない）が、基準は言える。
  **これは下の「STUB に acceptance を渡さない」に触れない** ── あの規則は*モデル*から
  基準を遠ざけるもので、ここでは何もモデルに見せず、値は全部番兵のまま。
  `__stub__` を併置するのは、基準の言うキーだけにすると**キー集合の比較が一致する**から
- **parse できないものは生成しない。** `None` を返してソルバーに戻す。コンパイルできない
  スタブを作るのは、置き換えた問題より悪い。Python は現状すべてソルバーのまま
- **C# は番兵の値を使わない。** メソッド、コンストラクタの本体を
  `throw new System.NotImplementedException("__stub__");` にし、フィールドと自動プロパティは
  宣言のまま残す。bool には誤った値が無く、文字列をキャストして押し込む手は
  `InvalidCastException` になる（実測）。R5 はこの印の付いた例外（`StubNotImplemented`）と
  アサーションだけを赤と認め、印の無い `NotImplementedException` は拒む。名前空間は柵の中の
  フォルダから作り、ほかのフォルダの型は `using` で持ち込む。契約に Unity の型が現れ、Unity の
  参照があれば `using UnityEngine;` を足す。TEST_WRITE のブリーフは、スタブのフィールドが既定値
  （参照型なら null）であることを伝え、使う前に `Assert.IsNotNull` を置かせる
- **C# の入れ子の型もランナーが書く。** 契約の `class Board.Cursor` と `int Board.Cursor.Position` は、
  Board の中の入れ子の型とそのメンバーを表す。入れ子の型は外側の型のメンバーの後ろに丸ごと置き、
  型の頭に `public` を付ける。C# の入れ子の型の既定は private だからだ。ソルバーに書かせると、
  入れ子のクラスを private のまま置き、外側の static メソッドをその中に入れた（取り込んだ Unity の
  プロジェクトの S1、2026-09-30）

配線前に、生成物を実際に vitest にかけて確認した ── **`toBe(false)` を期待するテストも
`toBe(true)` を期待するテストも落ちる。** モデルが値を選んでいる限り boolean には
持たせられなかった性質。

### 5-2. ソルバーに渡さないもの

STUB をソルバーに書かせるとき（Python と、ランナーが parse できなかったとき）、ブリーフには
**シグネチャ以外を一切載せない**。意味を運ぶものを載せるとソルバーはそれを忠実に実装し、
その受け入れ条件は RED_GATE で通ってしまう（契約に `raises` を書いて実際にそうなった）。

同じブリーフで、番兵値が**署名の述べる形**を持つことを要求する ── タプルは注釈と同じ
要素数、辞書は呼び出し側が引くキー、データクラスは全フィールド。テストはアサーションの前に
返り値を分解するので、分解できない値は**赤いテストではなく壊れた呼び出し**になり、R5 が
拒否して誰も直せなくなる。**目立つ番兵値**も明示的に要求する（§4-1）。「型が合っていて
間違った値」だけでは、ソルバーが `""` や `0` を選んだ瞬間に境界条件が正解してしまい R4 で
止まる。併せて「検証・型チェック・分岐を一切書かない」ことも指示する。

**入力量はモジュールの数に依存しない**（依存先の数にのみ依存する）。
BOOTSTRAP 1-5 の「1回あたりの入力量が一定」はここで実現される。

### 5-3. 既存のファイルのスタブ

`files_write` のうち HEAD にあるファイル（取り込んだリポジトリのコード）では、スタブは
**`provides` の名前の宣言だけを差し替える。** ほかの関数、クラス、定数、import、コメントは
残す。丸ごと書き直すと、モジュールに関係の無い関数まで消える。

- **TypeScript はランナーが差し込む。** HEAD の中身を最上位の文に切り、`provides` の名前を
  宣言する文を生成したスタブの宣言に置き換える。ファイルに無い名前は末尾に足す。差し替え
  なかった部分がすでに import か宣言している名前には、import を足さない（同じ名前を2度
  import すると esbuild がファイルごと拒む）。1つの文が2つ以上の名前を宣言していれば
  （`const a = 1, b = 2`）、`None` でソルバーに回す
- **C# はランナーがメンバーの本体だけを差し替える。** C# の宣言は型の中にあるので、単位は
  メンバー（`Board.Score`）。署名が契約と同じメンバーは、本体（`{ ... }` か `=> ...;`）だけを
  `throw new System.NotImplementedException("__stub__")` にし、属性、修飾子、コメントは残す。
  プロパティはアクセサの本体を替え、自動プロパティとフィールドは残す。型に無いメンバーは
  型の末尾に足し、それが口にするほかの名前空間の型に `using` を足す。署名が契約と違う
  （署名を変えるモジュール、オーバーロード）、型がファイルに無い、本体の無いメソッド、
  enum か interface の中身が契約と違う、契約の入れ子の型と同じ名前のものがもう型の中にある、
  のどれかなら `None` でソルバーに回す。ファイルに無い入れ子の型は、外側の型の末尾に足す。走査は
  文字列（逐語的 `@""`、補間 `$""`）、文字リテラル、コメントを飛ばし、`#if` はテストの
  ビルドと同じシンボルで評価する
- **ソルバーに頼むときは、ブリーフに既存のファイルを列挙する。** 挙げた名前の宣言だけを
  変え、ほかの行はそのまま残せ、と書く
- **書いた後にランナーが比べる。** 最上位の文のうち `provides` の名前を宣言しないものが、
  HEAD にあったものとすべて同じであること。Python は `ast.dump` で比べるので、空白と
  コメントの違いは数えない。TypeScript は空白を詰め、末尾の `;` を外した文で比べる。
  import は比べない。スタブは新しい型のために import を足すことがあり、足りない import は
  コンパイルで必ず分かる。名前の一部だけを `provides` が挙げる文は、差し替えれば必ず
  変わるので比べる側に残す。C# は型の頭（属性、修飾子、基底）とメンバーの1つずつを比べる。
  クラスを1つの単位にすると、1つのメソッドの差し替えでクラス全体が変わったことになる。
  `#if` の条件が偽の範囲もそのまま比べる（`UNITY_EDITOR` の中は Unity のエディタで動く）。
  違えば STUB で止める

比べるのは STUB の直後だけ。消えた関数は、それを使う既存のテストを VERIFY で落とすが、
そのときには、どの位相の誰が消したのかがもう分からない。IMPL が同じファイルのほかの
関数に触れるのは許す。守るのは既存のテストの PASS_TO_PASS だ。

## 6. 設計仕様書と受け入れ条件

### 6-1. 置き場

```text
docs/
  spec/        # 人間が書いた仕様書。spec import が human/in/spec/ から写す
  basic/       # 基本設計仕様書。上流の成果物
  modules/     # 詳細設計仕様書。中段の成果物
    <dir>/
      <name>.md   # src/<dir>/<name>.<ext> のモジュール
ac/
  <dir>/
    <name>.json   # そのモジュールの受け入れ条件。コミットしない
```

- `docs/` の中身は日本語で書き、人間が読む。ランナーが読むのは節の区切りと契約のブロックだけで、
  文の中身は判断しない
- モジュールは1ファイルを単位とする。モジュールの id は `src/` の下のパスから拡張子を
  落としたもの（`game/board`）。使える文字は英数字、`_`、`-` で、`/` で区切る
- C++ はヘッダとソース（`.h` と `.cpp`）の対で1モジュール、1つの詳細設計仕様書にする
- 振る舞いの無い型（構造体、列挙、データだけのクラス）は単独のモジュールにしない。
  使うモジュールに含めるか、共有の型のモジュールにまとめる
- `docs/`、`ac/`、`plan/` は 0700 runner。柵の場所（`layout.json`）をこの下に置くことはできない

### 6-2. 基本設計仕様書の形

- `basic/` の下のファイルを合わせて、`## 概要` の節がちょうど1つある。概要には目的と構成だけを
  書き、具体的な値は書かない。すべてのモジュールのソルバーがこの節を受け取るので、値を書くと
  モジュールの設計と競合する
- 各ファイルの本文（見出しを除く）が日本語で書かれている

### 6-3. 詳細設計仕様書の形

- `## 振る舞い` と `## 契約` の節をちょうど1つずつ持つ
- 言語指定 `ndjson contract` のコードブロックをちょうど1つ持つ。1行が JSON の1件で、
  次のどれか

```json
{"provides": "<署名>"}
{"provides": "<署名>", "entry": true}
{"requires": "<署名>", "from": "<モジュール>"}
```

- provides を少なくとも1行持つ
- 契約のブロックと見出しを除いた本文が日本語で書かれている
- 署名は契約にだけ書く。本文には振る舞いと意図を書く
- `"entry": true` は、この設計の外から呼ばれる provides に付ける。プログラムの起点、
  フレームワークが呼ぶもの、既存のコードが呼ぶもの、ライブラリの公開 API がこれに当たる
- requires の `from` は、この設計のモジュールか、どのモジュールも書き直さない既存の
  ファイル（`src/` の下のパスから拡張子を落としたもの）

署名の形は言語ごとに決まり、`contract_note` がブリーフで伝える。名前は
`provides_pattern` で読み、requires と provides はその名前で突き合わせる。

| 言語 | 例 | 名前 |
|---|---|---|
| Python | `def score(board: Board) -> int` | `score` |
| TypeScript | `export function score(board: Board): number` | `score` |
| C# | `static int Board.Score(Board board)` | `Board.Score` |
| C++ | `int Board::score() const` | `Board::score` |

### 6-4. 受け入れ条件の形

```json
{"criteria": [
  {"case": "normal", "kind": "unit", "given": "a 3x3 board", "then": "returns 9"}
]}
```

- 1件はちょうど `case`、`kind`、`given`、`then` の4つの空でない文字列を持つ
- `case` は `normal`、`boundary`、`error` のどれかで、3つとも揃っている
- `kind` は `unit` か `integration`。`integration` は requires を持つモジュールだけが持てる
- `then` が単独で具体的な値を述べる。数、引用符で囲んだリテラル、例外の型、空のコレクション
  （`[]` `{}` `()`）、`True` / `False` / `None` のどれか（`CONCRETE`）
- 前提が反射（`typeof`、`GetType`、`hasattr` など）で、結果がコードの形（メソッドを持つ、
  基底型、名前）を主張する条件は拒む。スタブはすでに契約どおりの形を持つので、その
  テストは実装の前に通り、R4 で必ず止まる
- 1件の条件が1つのテストになる。テストの数は条件の数と同じ（R1）

### 6-5. インターフェースチェック

中段の出口で、ランナーが契約を機械的に確かめる。振る舞いは確かめない。振る舞いは
単体テストと統合テストが受け持つ。

| 検査 | 内容 |
|---|---|
| 存在 | requires の名前を、`from` のモジュールが提供している。`from` が既存のファイルなら、その HEAD の宣言にある |
| 署名の一致 | この設計のモジュールから求める署名が、提供する provides の行と同じ（空白の違いは数えない） |
| 依存の循環 | モジュールの依存に輪が無い |
| 未使用 | どのモジュールも求めない provides が無い。`"entry": true` の行は除く |
| 形 | provides の中のコンテナ型が中身を述べている（`dict[str, int]`、`List<Cell>` など） |
| 居場所 | 1つの名前を提供するモジュールは1つ |

ほかに、2つのモジュールのテストのファイル名が重なれば拒む。C# のクラス名と C++ の
スイート名はファイル名から決まり、重なると2つのモジュールのテストが同じ名前で選ばれる。

結果は `plan/INTERFACE.json` に、依存の順、依存先、入口の行と一緒に書く。依存の図と入口の行を
人に見せるための記録だ。

`check` は同じ検査を、誰も呼ばずに今の設計に流す。

### 6-6. 下流の計画

`modules approve` は設計から `.runner/tasks.json` を作る（`build_tasks`）。受け入れ条件を
含むので、コミットしない。モジュールは依存先が先に来る順に並ぶ。

| キー | 中身 |
|---|---|
| `id` | モジュールの id |
| `kind` | 依存先があれば `integration`、無ければ `unit` |
| `depends_on` | この設計の中の依存先 |
| `contracts.provides`、`contracts.requires` | 契約の署名に置き場を添えた行（`legacy_line`）。Python は `-- defined in <モジュール>`、ほかは `<ファイル>: ` を前に付ける |
| `acceptance` | 受け入れ条件 |
| `files_write` | モジュールのファイル |
| `files_test` | 単体テストのファイルと、統合の条件があれば統合テストのファイル。名前は言語の決まりに合わせる（`tests/test_game_board.py`、`tests/game/BoardTests.cs` など） |
| `expected_tests` | 条件の数 |
| `max_attempts` | 3 |
| `design` | 詳細設計と受け入れ条件のハッシュ。緑のときに台帳に残す |
| `context` | §5 の背景 |

## 7. 台帳、止まったとき、再開

### 7-1. 台帳 `plan/ledger.jsonl`（追記専用・runner 所有）

```json
{"ts":"2026-10-14T10:22:31+0900","event":"RED_GATE","step":"game/board","result":"pass","tests":5}
{"ts":"...","event":"VERIFY","step":"game/board","attempt":1,"backend":"claude","green":false}
{"ts":"...","event":"FAILED","step":"game/score","phase":"VERIFY","modules":["game/score","game/board"]}
{"ts":"...","event":"SENT_BACK","modules":["game/score"]}
{"ts":"...","event":"GREEN","step":"game/score","attempts":2,"design":"<ハッシュ>"}
```

台帳は段のコマンドと GREEN のコミットに入る。緑のモジュールは台帳の `GREEN` から数え、
`REOPEN` がその緑を取り消す。

### 7-2. 下流で止まったとき

モジュールが RED_GATE、凍結の照合、経路許可で止まるか、試行を使い切ると、ランナーは
（`fail_module`）:

1. `plan/FAILURE.md` に止まった位相、理由、試行、落ちたテスト、関わったモジュールを書く。
   関わったモジュールは、止まったモジュールと、テストが落ちたモジュール
2. 段を `midstream`、`open` を `[]` にする
3. 台帳に `FAILED` を書き、`FAILURE.md`、段、台帳をコミットする

`open` が `[]` のあいだは、`modules draft` も `modules approve` も拒む。人間が
`reopen <モジュール>...` で詳細設計を直すモジュールを選ぶ。複数選べる。プランナーは
選ばれたモジュールの詳細設計と受け入れ条件だけを直せる（§3-3）。人間は直させずに
そのまま `modules approve` で流し直すこともできる。

`modules approve` は、設計のハッシュが変わった緑のモジュールと、まだ緑でないモジュールを
下流に流す。

最終確認（`review`）で人間が差し戻すときも、同じく `reopen` で直すモジュールを選ぶ。

### 7-3. 設計を差し戻さずに止まるもの

次の3つは、設計にもソルバーにも落ち度が無い。中段に戻さず、段は `downstream` のまま止まる。

| 止まり方 | 終了コード | 台帳 | 次の操作 |
|---|---|---|---|
| 箱が書き込みを拒んだ（ソルバーかビルドの出力に、柵の中への `EACCES`、`EPERM`、`EROFS`、`ENOSPC`） | 6 | `INFRA_FAILURE` | 権限を直し、`reset <モジュール>` の後に `run --all` |
| 利用枠が待っても戻らない | 5 | `QUOTA_WAIT` | 枠が戻ったら `reset <モジュール>` の後に同じコマンド |
| 最初のモジュールの前に、既存のテストが落ちている | 2 | `BASELINE` | 既存のテストを直す |

`plan/`、`docs/`、`ac/` や凍結したテストへの書き込みが拒まれたのは、柵が効いた証拠だ。
ソルバーの誤りとして扱い、試行を使う。

### 7-4. やり直し

`reset <モジュール>` は、作業ツリーを最後のコミットに戻し、緑でないモジュールのテストと
凍結のマニフェストを消す。順番に意味がある。

1. 柵の中のファイルを引き取り、書けるようにする（FREEZE は `tests/` を読み取り専用にし、
   git は書けないディレクトリの中のファイルを消せない）
2. `git reset --hard HEAD` と `git clean -fdq`
3. 柵のディレクトリを作り直す。取り込んだブランチでは、柵に追跡されたファイルが無く、
   `git clean` が柵ごと消すことがある
4. 台帳を書き戻す。台帳は git の管理下にあるので、`reset --hard` が捨てる試行の記録を消す

`reopen` も最初に同じことをする。

### 7-5. 走行の設定

上限、やり直しの方針、ソルバーの段は `/srv/loop/settings.json`（root 所有）に置く。
下流の計画はランナーが設計から作るので、人が書く場所はそこに無い。無ければ既定で走る。
知らないキーがあれば止まる。

```json
{"solver_tiers": ["local", "claude"],
 "policy": {"retry": "resample"},
 "limits": {"attempts": 8},
 "timeouts": {"solver": 1800}}
```

| キー | 中身 | 既定 |
|---|---|---|
| `timeouts` | `test`、`solver`、`planner`、`critic` の秒数 | 120、960、1800、900 |
| `limits` | `revisions`（設計の書き直し）、`attempts`（全モジュールの試行。0 はモジュールの値）、`test_writes`（テストの書き直し） | 3、0、3 |
| `policy` | `retry`: `repair` か `resample`（§4-4-1） | `repair` |
| `solver_tiers` | ソルバーのバックエンドの名前の並び（§4-4-1） | `["claude"]` |

## 8. CLI

`sudo -u runner python3 /srv/loop/runner/loop.py <コマンド>` で呼ぶ。保守ユーザーは
`loop` のコマンド（COMMANDS.md）から使う。

```text
spec import                     # §3-2
basic draft [--language <言語>] [--framework <持ち込む先>]
basic approve
modules draft                   # 書いた後に modules critique を続けて流す
modules critique
modules approve
reopen <モジュール>...
check                           # 今の設計を検査する。誰も呼ばない
status                          # 段とモジュールごとの状態
run <モジュール>                # 1モジュール
run --all [--budget <分>]       # 依存の順に、緑でないモジュールを回す
reset <モジュール>              # 止まったモジュールを捨て、最後のコミットに戻す
```

### 8-1. `run --all` の停止条件

```text
モジュールを回す → 緑なら次へ
                → 止まれば、中段に戻して終わる（§7-2）
```

止まるのは次だけで、**すべてリポジトリか台帳に対する客観的事実**。

| 停止条件 | 終了コード |
|---|---|
| 全モジュールが緑。段を `review` に移す | 0 |
| モジュールが止まり、中段に戻った | 2 |
| `--budget` の壁時計を使い切った（モジュールの切れ目で判定） | 2 |
| 利用枠が待っても戻らない | 5 |
| 箱が書き込みを拒んだ | 6 |

計画は始めに1回読む。緑のモジュールは台帳から判別して飛ばすので、**中断しても
モジュールの境界からは再開できる**（位相の途中からは §10-5 のまま未対応）。

### 8-2. 終了コード

| code | 意味 |
|---|---|
| 0 | 成功 |
| 1 | 前提不足（段が違う、設計が無い、柵が開いている、など） |
| 2 | 停止・拒否（検査に落ちた、プランナーが検査を通る設計を書けなかった、モジュールが止まった） |
| 5 | 利用枠 |
| 6 | 箱の故障 |

**自動で次の段へ進む経路は無い。** 段を進めるのは人間の承認だけだ。

1. ~~**ソルバーの動作条件**~~ — **決着済み**:
   - **実体**: 既定は Claude Code（`solver-claude`）。ランナーが渡すのはバックエンドの
     *名前*だけで、名前から実体への対応は root 所有の `bin/solver-run` が持つ
     （§4-4-1）
   - **ツール**: `Read` `Write` `Edit` だけを許し、`Bash` は禁止する。テストを走らせる
     許可は、自分の書いたコードを動かす許可と同じだから。`smoke-pytest` がこれを確かめる
   - **認証の渡し方**: `claude setup-token` のトークンを `/etc/loop/solver.env`
     （`root:solver 640`）に置く。planner と critic も同じ形で、それぞれ自分のファイルだけを
     読める。Codex を使う場合は `solver` 自身の対話ログイン
     （`sudo -u solver -H codex login --device-auth`）で、`/home/solver/.codex`（0700）に落ちる
   - **egress 制限下で動くか**: `60-egress.sh` は**意図的に未適用**（provision/README §4）。
     Claude の API への通信は要るので、締めるならプロキシ構成で API のドメインだけを通す
2. **プロキシ構成の要否** — §1-3 の簡易版で始め、IP 変動で壊れた時点で上げるか、最初から立てるか
3. **`.venv` の作成タイミング** — プロビジョニング時に `runner` が作り、以降 solver からは
   読み取り専用。依存の追加は人がプロビジョニングで行う、で確定してよいか
4. **テスト実行のタイムアウト値** — 無限ループする実装が普通に出るので必須。
   モジュールごとに指定させるか、全体固定（`settings.json` の `timeouts.test`、既定 120s）か。
   **プランナー側は実測で 1800s に引き上げた**（2026-08-21）。
   引き上げと同時に、**その値を `solver-run` / `planner-run` へ渡すよう直した** ──
   両スクリプトは第2引数が無いと `900` を使うので、`TIMEOUTS` だけ上げても
   実際に効く上限は動かない。run 5 は loop.py に 1800 と書いてある状態で
   **900 秒で2回殺された**。ランナー側の `subprocess` タイムアウトは
   `+BACKSTOP_MARGIN`（120s）で、スクリプトの `--kill-after=30` の外側に置く。計画に要した時間は
   8分（run 4）・12分（run 3）・16分超（run 5、旧 960s で打ち切り）で、
   **規則が増えるほど伸びる**（規則は全部、書き出す前に満たすべき条件になる）。
   加えて Claude Code はファイルを最後にまとめて書くので、打ち切られた呼び出しは
   **部分的な設計すら残さない**。低すぎる設定の代償が高すぎる設定より大きい
5. **VM が落ちた場合の再開の粒度** — §1-6。位相の途中（例: IMPL のソルバー実行中）で
   VM が消えたとき、台帳の最終行から何をやり直すか。試行回数に数えるかどうかも決める
6. **最終確認の承認** — 段 `review` の承認と下書きのプルリクエストはホストの作業で、
   ランナーは段を進めない。承認の後に段をどう閉じるか

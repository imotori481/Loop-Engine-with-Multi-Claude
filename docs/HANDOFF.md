## 1. このプロジェクトは何か

**ループエンジニアリング**の基盤づくり。AI に実装させるループを、
「テストが通った」が自己申告にならない形で回すための仕組みを作っている。

役割分担:

| 主体 | 実体 | 担当 |
|---|---|---|
| **プランナー** | Claude Code（サンドボックス内・uid `planner`） | 仕様と受け入れ条件を書く。コードは書かない |
| **ランナー** | **`runner/loop.py`（v1・実装済み）** | 関門を機構として強制する。AI ではない |
| **ソルバー** | Codex CLI（サンドボックス内） | 実装を書く。記憶を持たず、1ステップ分の情報しか受け取らない |

AI は両端の2つだけで、真ん中は普通のプログラム。**関門の値打ちは判断しないことにある**ので、
そこに AI を置かない。

## 4. 基盤の切り替え（旧ブロッカーの解消）

以前のブロッカーは「VM が起動時に2回に1回ハングする」だった。原因はハイパーバイザ層で、
ホストの Hyper-V が有効なため VirtualBox が NEM モードに落ちていた。
`--paravirtprovider` を変えても頻度が下がるだけだった。

**Hyper-V を止めずに VirtualBox を捨てる方を選び、WSL2 に移した。**
Hyper-V を無効化すれば VirtualBox は安定するが、WSL2 と Docker Desktop が動かなくなる。
経緯と得失の比較は `provision/README.md` §6。

移して**得たもの**: 起動の安定性、構築時間の短縮（ISO の無人インストールが不要）。
移して**失ったもの**:

- **無人実行**。WSL2 の VM は約60秒のアイドルで停止し、SSH のトラフィックはアイドル判定に
  数えられない。keepalive タスクがログオンセッションに紐づくので、
  **ログオフを跨いでループは回せない**（RUNNER_SPEC §1-6）
- **既定の隔離**。WSL2 は既定で `/mnt/c` が見え `.exe` が動く。切ったうえで
  `05-isolation.sh` が実状態に対して assert する（RUNNER_SPEC §1-4）
- **軽いスナップショット**。`wsl --export` は差分が取れず数 GB

### ソルバーを差し替えるための三つ（2026-09-01 実装）

**きっかけは費用。** ローカルの 9B クラスをソルバーに据え、Codex より弱いことを織り込んだ
うえで、落ちた理由を次のプロンプトに積む、という提案。

まず事実の訂正: **「落ちた理由を次に渡す」は最初から入っている**（`brief_impl` の失敗欄。
初回は RED_GATE の `failure_kinds`、以降は VERIFY 出力の末尾3000字、skip と回帰には
構造化した前置きが付く）。だから提案の中身は新規実装ではなく、**既にある機構が弱い
ソルバーでも効くか**という調整だった。

次に財布の訂正: solver は Codex（ChatGPT）なので `run --all` は Claude をほぼ使わない。
Claude を使うのは対話セッションと**プランナー**（bootstrap / propose / plan revise）。
ここから弱いソルバーの本当の危険が見える ── **試行を使い切るとエスカレーションになり、
エスカレーションはプランナー呼び出し、つまり Claude を使う**。ソルバーを安くすると費用が
プランナー側へ移る経路がある。だから測るべきはトークンではなく**エスカレーション回数**。

対策を3つ入れた。いずれも既定値では**挙動が1バイトも変わらない**。

| | 何をしたか | なぜ |
|---|---|---|
| 1 | `limits.attempts` で全ステップの `max_attempts` を一括上書き | 適切な回数は**誰が試行の代金を払うか**で決まり、プランを書く時点のプランナーはそれを知らない |
| 2 | `policy.retry: "resample"` ── 試行ごとに木を捨て、独立した抽選にする | 弱いソルバーは自分の失敗を直せず損傷を積む。ランナーは厳密な検証器なので抽選が成立する |
| 3 | `solver_tiers: ["local","codex"]` ── 安い段が試行を使い切ってから高い段へ | 使い切った先はエスカレーション＝**プランナー呼び出し**。2段目は追加の出費ではなく、安いほう |

**2 は既存の穴でもあった。** 木の巻き戻しは**エスカレーションの後にしか走っていなかった**
ので、attempt 3 は attempt 2 の壊れたコードを引き継いで始まっていた。§6-2 は
エスカレーションの粒度で既に「失敗した実装はソルバーに渡さない。壊れた方針への固着を
避けるため」と書いていたのに、1つ内側では逆をやっていた。

巻き戻しに `git reset --hard` は使えない。**このステップのテストはまだコミットされて
いない**（コミットは GREEN）ので、満たそうとしている当のテストが消える。戻すのは
`files_write` のパスだけ ── 経路許可が「変わったのはここだけ」と確認済みの集合と同一。
台帳には `DISCARD` が残る。

`solver-run` はバックエンド名で分岐するようになった。ランナーが渡すのは**名前だけで
コマンドではなく**、`/srv/loop/bin/solver-<name>`（root 所有 0755、引数は
`<brief> <seconds>`）を置くのは sudo を持つ人間の仕事。**これが2つ目のソルバーの統合面の
全部**で、書き込みの柵も1ブリーフの経路も走る uid も、エージェントではなく uid と
ファイルシステムの性質なので、何が動いても既に正しい。

ランナーのテストは 28 → **39**（`runner/tests/test_attempts.py`）。

**`solver-local` は実装済み**（2026-09-01）。手順・失敗表・観測項目は `LOCAL_SOLVER.md`
に分けてある ── **Claude を介さずに最後まで進めるため**の文書で、費用の正体が
「動かすこと」ではなく**曖昧な失敗が生む往復**だという訂正（同日）に対する答え。
`bin/solver-local`（単発・全文出力・json_schema 拘束）、`bin/llm-serve`、
`bin/smoke-local`（7項目の自己診断）、`70-local-solver.sh`。

**設計上いちばん効く判断は終了コードの使い分け。** 非ゼロは `Halt` → エスカレーション →
**プランナー呼び出し**なので、「モデルが下手」は**必ず 0 で返す**（試行を1回消費して
終わり、Claude には届かない）。非ゼロにするのは機械が間違っているとき ── サーバ不達、
ブリーフ書式の破れ、コンテキスト超過 ── つまり**再試行しても無駄で、人間が見るしかない**
場合だけ。

書くときの確定事項が1つ:
**ローカルモデルは nonthinking で走らせる**（2026-09-01 指示）。推論オプションが載る
場所は `bin/solver-local` の中で、ランナー側には無い ── ランナーが知ってよいのは
バックエンドの名前だけ、という §4-4-1 の線をここでも越えない。

これは `policy.retry` の選び方に効く。思考を出さないモデルは失敗文面から自己修正する
余地がその分小さいので、`repair` の期待値が下がり、**`resample`（独立した抽選）が
既定にふさわしくなる**方向に働く。1本目は `resample` で回す。

**回す前に決めること: 報酬ハッキングの機械的対策。** 失敗出力を返す × 弱いモデル ×
試行回数を増やす、の3つが揃うと「テストを通すためのハードコード」が主要な失敗モードに
なる。FREEZE はテストの改変を止めるが `if n == 3: return 7` は止めない。案は
**ホールドアウト** ── プランナーがテストを可視群と秘匿群に分け、ブリーフには可視群だけを
描画し、RED_GATE と VERIFY は全部を走らせる。判断を含まない純粋な機構である点で設計に
合う。ただし**現状 IMPL 中の `tests/` は 0444 でソルバーから読める**ので、いまのままでは
要請であって剥奪ではない。本物にするには IMPL 中の `tests/` を runner のみにする必要が
あり、代償として**ソルバーが自分で pytest を回して自己検証できなくなる**。弱いモデルほど
それは効く機能なので、ここは代償のある判断。

**次の一手は統制実験。** run 5 の `tasks.json` をそのまま流し、**ソルバーだけを差し替える**。
題材を変えると「モデルが弱い」のか「その題材が難しい」のかが分離できない。この実験は

### UI を機械に見せる ── Node/DOM の土台（2026-09-02 夜・実装済み）

run 7 の欠陥4と5は、どちらも**「UI が関門の外にある」**という一つの原因から出ている。
tkinter は画面が無いと駆動できず、画面はサンドボックスに無い。だから計画は UI を
`main()` という薄い殻に追い出し、検査できる部分だけを厚くした ── **検査できる部分＝
テキスト**になり、見た目が端末的になり、そして殻の中で起きることは誰も見なかった。

**DOM は画面を要らない。** happy-dom がメモリ上に document を作るので、テストが
ボタンを押して変化を確かめられる。「押せるものがあるか」が、人間にしか答えられない
問いから**ただの赤いテスト**になる。

実測（`provision/bin/smoke-dom`、書く前に確かめた）:

```
working UI:   3 test(s), 0 failure(s)
run 7's UI:   3 test(s), 2 failure(s)
  message="expected 0 to be greater than 0"
  message="Cannot read properties of null (reading 'click')"
```

**両方向を見るのが要点。** 何でも通す関門は、働いている関門と見分けがつかない。
`expected 0 to be greater than 0` が、run 7 で誰も見られなかったものそのもの。

vitest の JUnit XML は pytest と同じ形（`testsuites`/`testsuite`/`testcase` に
tests/failures/errors/skipped）なので、**ランナーの判定部はほぼそのまま使える。**

#### スタブをランナーが書くようにした

S1 を13回止めていた最後の原因がこれだった。温度を下げたらスタブが**正解**を返すように
なる ── `return {resource: 0, generators: {}, lastUpdate: 0}` は createGame の正しい
初期状態で、R4 で止まる。ブリーフは「既定値を返すな」と明示している。**届いて、
読めて、無視された**（`return false` のときと合わせて2度、別の設定で）。

契約が署名も型の中身も置き場も持っているので、**組み立ては決定的**にできる。
配線前に生成物を実際に vitest にかけて確認した ── **`toBe(false)` を期待するテストも
`toBe(true)` を期待するテストも落ちる。** モデルが値を選んでいる限り boolean には
持たせられなかった性質。

parse できないものは `None` を返してソルバーに戻す。**コンパイルできないスタブを
生成するのは、置き換えた問題より悪い。**

辞書型には**受け入れ条件が引用しているキー**を入れる（`CATALOG.cursor.rate` は
cursor が無ければ比較の前に落ち、R5 になる）。これは STUB が基準を見てはいけないと
いう規則には触れない ── あの規則は**モデル**から基準を遠ざけるもので、ここでは
何もモデルに見せず、値は全部番兵のまま。`__stub__` を併置するのは、基準の言うキー
だけにすると**キー集合の比較が一致してしまう**から。

#### 残った失敗は3件とも「基準 → テストコード」の翻訳

| | 症状 | 実際 |
|---|---|---|
| S3 | 実装が6回とも落ちる | 期待値リテラルから `{` `}` が落ちていた |
| S4 | R5 | `expect(...).deepEquals(...)`。基準の散文「deep-equals」をメソッド名にした |
| S5 ① | 実装が6回とも落ちる | **モックの `getItem` が `""` を `null` に潰していた** |
| S5 ② | R5 | `vi.mocked(...).mockClear is not a function` |

**3件とも基準は正しく、実装も正しい。** S5 ① では
`return storage.getItem(KEY)` という完全に正しい実装が6回書かれて6回落ちた ──
テストが自前で書いた偽 Storage が `data[key] || null` だったため。

そして**凍結されるので後から誰にも直せない。** BOOTSTRAP 1-1 が「唯一の漏れ口」と
呼んでいた場所そのもので、REVIEW_GATE はそこに置く関門だが v1 では飛ばしている。

引き直せば直ることは S3・S4 で実証された。ただし**毎回人間が中身を読んで `reset` を
打っている。**

## 6. 触るときの注意

- **`wsl --shutdown` を使わない。** keepalive プロセスが巻き添えで死に、
  SSH が使えなくなる。使ったら `schtasks /run /tn "WSL-keepalive-Ubuntu-24-04"`
  （`provision/README.md` §3-2）
- **SSH 秘密鍵は持ち込まない。** 移設先で作り直す。**生成は必ず Bash で行う**
  ── PowerShell からだと `-N ''` が空パスフレーズにならず、生成は成功するのに
  署名できない鍵ができる（§3-5）
- **`.ps1` に日本語を書かない。** PowerShell 5.1 が ANSI として読み、コメントが
  次の行を飲み込んで変数が黙って null になる（§3-6）
- ディストロには `/mnt/c` が無い。ファイルの受け渡しは scp（§2-5）

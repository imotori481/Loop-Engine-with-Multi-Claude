# Loop Engine with Multi-Claude

要件を渡すと、Claude Code が計画を立て、テストを書き、実装し、テストが通るまで回す実行基盤。
テストが通ったかの判定は AI に任せない。普通のプログラムが機械的に確かめる。

[Nakano-official 氏の Loop-Engine](https://github.com/Nakano-official/Loop-Engine) をフォークし、
AI の担う役をすべて Claude Code で動かす形にしたもの。Claude のサブスクリプション1つと、Windows の
WSL2 があれば動く。追加の機材は要らない。

## 4つの役

作業は4つの役で分担する。AI の役は互いの成果物を書き換えられない。

| 役 | 中身 | すること |
|---|---|---|
| プランナー | Claude Code | 要件をステップに分け、ステップごとに満たすべき条件を書く |
| クリティック | Claude Code | プランナーの計画を読み、要件を満たさない箇所を指摘する |
| ソルバー | Claude Code | ステップごとにテストを書き、実装する |
| ランナー | 普通のプログラム | 上の3役を順に呼び、テストの結果で次に進むかを決める |

## できること

### 要件から最後まで任せる

要件を書いたファイルを1つ渡すと、計画づくりから全ステップの実装までを流す。

- プランナーが計画を立て、クリティックの指摘を受けて直す
- ソルバーがステップごとにテストを書く。ランナーは、実装する前にそのテストが落ちることを確かめる。最初から通るテストは何も確かめていないからだ
- ソルバーが実装する。ランナーは、テストが通ることを確かめる。通らなければやり直させ、回数の上限に達したらプランナーに計画を直させる
- 全ステップのテストが通ると、人が動かして確かめるのを待って止まる

AI の役は、Windows から切り離した専用の WSL2 の中で動く。ブラウザや端末を閉じても止まらない。

### 対応する言語

| 言語 | テスト | 画面なしで確かめられるもの |
|---|---|---|
| Python | pytest | ロジック |
| TypeScript | vitest + happy-dom | ロジックと、ボタンを押して表示が変わるまでの UI |
| C# | NUnit（.NET 8）。コードは netstandard2.1 / C# 9 でビルド | ロジック。Unity のプロジェクトなら、その参照アセンブリでコンパイルする |
| C++ | GoogleTest（C++17） | 標準のロジック。DXライブラリや Windows の API を使うファイルはビルドから外す |

### 既存リポジトリで作業させる

GitHub のリポジトリのブランチを取り込み、その上で走らせる。既存のコードを書き換えさせられる。

- ソルバーが書き込める場所をプロジェクトごとに決める。既定は `src/` と `tests/`
- 既存コードの公開されている型や関数をプランナーとクリティックに渡す。計画はそれらを使える
- 走る前に既存のテストが通るかを確かめ、落ちていれば止まる。既存のテストはソルバーが書き換えられないので、振る舞いを壊すとそのテストが落ちる
- 人が確かめて承認すると、元のブランチへの PR を出す。作業用に置いたファイルと計画は PR に入らない

GitHub の資格情報は Windows 側にだけ置く。AI の役が動く WSL2 には置かない。

### 複数のプロジェクトを切り替える

複数のリポジトリを名前で分けて扱う。切り替えても前のプロジェクトは消えず、戻せる。
同じプロジェクトで、要件を1つずつ積み重ねて走らせられる。前の要件の計画と記録は残る。

### 止まったときに手を入れる

- クリティックの指摘が直りきらずに止まったら、人が指摘を書き換えてから続けられる。的外れな指摘を外す、プランナーの問いに答える、といった使い方をする
- ランナーやプランナーが自力で進めなくなったら、人に問い合わせて止まる（エスカレーション）。画面から答えられる
- 途中で止まったステップは、最後にテストが通った状態に戻してやり直せる

## 使い方

操作は Windows 側のダッシュボードで行う。`host\loop-dashboard.cmd` を起動し、ブラウザで <http://127.0.0.1:8443> を開く。
環境構築は [provision/README.md](provision/README.md) と [host/README.md](host/README.md) に従う。

1. 要件を書く。手元だけで使う要件は `requirements/local/` に置く
2. 既存リポジトリで作業させるなら、「取り込み」タブでリポジトリとブランチを指定する
3. 「走行」タブで要件のファイルと言語を選び、開始する
4. 「いまの作業」と「ステップ」で進み具合を見る。誰が何をしているかが、試行の回数と経過時間と一緒に出る
5. 止まったら、「クリティックの指摘」やエスカレーションを読んで手を入れ、「走行」タブで続ける
6. 「ホストの写し」タブで成果を Windows 側に写し、動かして確かめる
7. 画面で承認する。既存リポジトリなら PR が出る。直してほしければ差し戻す

ほかに、プロジェクトの切り替え、役ごとのモデルと effort の変更、役ごとのトークン消費のグラフも画面にある。

`tailscale serve` で Tailscale のネットワークに出せば、スマホからも見られる。リモートからは差し戻し、エスカレーションへの回答、停止と続行ができる。承認と走行の開始はできない。

画面の詳細は [host/dashboard/README.md](host/dashboard/README.md)、端末から同じことをするコマンドは [docs/COMMANDS.md](docs/COMMANDS.md) にある。

## 仕組み

AI の3役は、Windows 側（以下、ホスト）から切り離した WSL2 の隔離環境（以下、箱）の中でそれぞれ別の uid（`planner`、`critic`、`solver`）で動く。何を見られるかは、プロンプトの約束ではなくファイルシステムが決める。

| 役 | 実体 | 見られないもの、できないこと |
|---|---|---|
| プランナー | Claude Code | 実装コードは書かない |
| クリティック | Claude Code | 計画の元ファイルもテストも読めず、承認もできない |
| ソルバー | Claude Code。ファイルの読み書きと検索だけを許す | 計画（受け入れ条件）を読めない。コマンドを実行できない |
| ランナー | `runner/loop.py`（標準ライブラリのみ） | ― |

ランナーは、次の関門を機械的に適用する。

- 実装前にテストが落ちること（Red）を確かめる
- 実装中はテストを凍結し、ソルバーに書き換えさせない
- 実装後にテストが通ること（Green）を確かめる
- 通らなければやり直させ、上限に達したらプランナーに差し戻す

ランナーがエージェントではなく普通のプログラムであることが、この構成の要点だ。関門に価値があるのは、判断をしないからだ。「惜しい」という理由で失敗を通す余地は、コードのどこにも無い。

各実行の全イベントは台帳（`plan/ledger.jsonl`）に `RED_GATE` / `FREEZE` / `VERIFY` / `GREEN` / `ESCALATED` / `USAGE` として残り、後から検証できる。

役ごとに、使うモデルと effort を `/etc/loop/<役>.env` の `LOOP_MODEL` と `LOOP_EFFORT` で決める。3役が同じサブスクリプションの枠を使うので、ランナーは利用上限に当たった呼び出しを失敗として扱わず、待ってからやり直す。呼び出しごとの消費量は台帳に残る。

中心となる原則は次のとおり。

- 受け入れ条件を作る者と実装する者を分ける
- ステップ間の情報は、ソースコードではなく、計画に書いた型や関数の取り決め（契約）で受け渡す
- 人間への確認条件を事前に固定する
- ソルバーに sudo やホストへのアクセス、コマンドの実行を与えない
- 判断が要らない仕事は機械がやる

全体像は [docs/ARCHITECTURE.md](docs/ARCHITECTURE.md) にある。

## 環境構築について

対象環境は Windows 上の WSL2 `Ubuntu-24.04`。構築作業はホストや WSL の設定、SSH 鍵、ユーザー権限、ネットワーク制御を変える。コマンドを抜粋して流さず、先に [provision/README.md](provision/README.md) の前提、手順、既知の落とし穴を通して読む。

WSL2 は既定のままでは隔離環境ではない。この構成では Windows ドライブの自動マウント、Windows 実行ファイルとの相互運用、WSLg を無効にし、プロビジョニング後に状態を検証する。普段使いのディストロとは別に、専用のディストロを作る。

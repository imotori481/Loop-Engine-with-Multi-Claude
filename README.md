# Loop Engine

AI に実装を任せるループを、テストの自己申告や権限逸脱に頼らず運用するための実験的な実行基盤です。

このプロジェクトでは、仕様と受け入れ条件を作る **プランナー**、関門を機械的に適用する **ランナー**、隔離環境内で実装する **ソルバー**、出来た計画の欠陥を指摘する **クリティック** を分離します。合格基準を作る主体と、それを満たす主体を分け、テストが実装前に失敗すること（Red）と実装後に成功すること（Green）の両方を確認します。

AI が担う3役（プランナー、ソルバー、クリティック）は、すべて Claude Code で動きます。追加の機材や、Claude 以外のサブスクリプションは要りません。

> [!IMPORTANT]
> ランナーは実装済みです。**3役すべてを Claude Code で動かし、要件から計画・実装・検証までを人間の介在なしに通した実行**があります（Python、8/8 ステップ）。
> ソルバーに Codex CLI やローカルの 9B モデルを使う構成でも、**要件6行から11ステップを通し切った実行**があります。
> 言語は **Python（pytest）** と **TypeScript（vitest + happy-dom）** に対応し、UI を画面なしで検査できます。
> 人間による事後監査（REVIEW_GATE）と、engine 自身の欠陥を機械が見つける仕組みは未着手です。

**役の分離は uid で行います。** 何を見られるかはプロンプトの約束ではなくファイルシステムが
決めます。全体像は [docs/ARCHITECTURE.md](docs/ARCHITECTURE.md) にあります。

## 仕組み

| 役割 | 実体 | 責務 |
|---|---|---|
| プランナー | 別 uid（`planner`）の Claude Code | 仕様、受け入れ条件、実行計画を作る。実装コードは書かない |
| ランナー | 通常のプログラム（`runner/loop.py`・標準ライブラリのみ） | Red、テスト凍結、検証、リトライ、エスカレーションを機械的に管理する |
| ソルバー | 別 uid（`solver`）の Claude Code。ファイルの読み書きだけを許し、コマンドは実行できない | 渡されたブリーフを基に実装する。計画（受け入れ条件）は読めない |
| クリティック | 別 uid（`critic`）の Claude Code | 適用前の計画を読み、要件を満たさない箇所を指摘する。**計画の元ファイルもテストも読めず、承認もできない** |

ソルバーのバックエンドは差し替えられます。既定は Claude Code で、Codex CLI とローカルモデルは計画の `solver_tiers` で名前を挙げたときだけ使います。

役ごとに、使うモデルと effort を `/etc/loop/<役>.env` の `LOOP_MODEL` と `LOOP_EFFORT` で指定します。3役が同じサブスクリプションの利用枠を使うので、ランナーは利用上限に当たった呼び出しを失敗として扱わず、待ってからやり直します。呼び出しごとの消費量は台帳に残ります。

ランナーが**エージェントではなく普通のプログラム**であることは、この構成の要点です。関門に価値があるのは、それが judgement を行わないからです。「惜しい」という理由で失敗を通す余地をコードのどこにも置いていません。

中心となる原則は次のとおりです。

- 受け入れ条件を作る者と実装する者を分ける
- 実装前にテストの Red を確認する
- 実装中はテストを凍結する
- リトライ上限への到達を、失敗ではなくプランナーへの差し戻しとして扱う
- ステップ間の情報はソースコードではなく contracts で受け渡す
- 人間への確認条件を事前に固定する
- ソルバーに sudo やホストへのアクセス、コマンドの実行を与えない
- **判断が要らない仕事は機械がやる** ── TypeScript のスタブは契約から決定的に組み立てられるので、ランナーが書く

## 動作実績

各実行の全イベントは台帳（`plan/ledger.jsonl`）に `RED_GATE` / `FREEZE` / `VERIFY` / `GREEN` / `ESCALATED` / `USAGE` として記録され、後から検証できます。

**Claude 単独構成 — テキストの単語出現数（Python）**

要件は関数3つ（正規化、分かち書き、出現数）です。3役すべてを Claude Code で動かし、`plan bootstrap` から `run --all` までを通しました。

| | 結果 |
|---|---|
| 無介入の緑 | 8/8 |
| ステップあたりの試行 | 全ステップ 1 attempt |
| エスカレーション | 0 |
| 最終スイート | 52件パス・回帰 0 |
| モデル | プランナー `claude-opus-5-5`、ソルバーとクリティック `claude-sonnet-5`、effort はすべて `medium` |

**run 5 と run 6 — 同じ計画、ソルバーだけを入れ替えた統制実験**

題材はアイドルゲームの中核ロジック。**入力は要件6行だけ**です。run 6 は run 5 の `tasks.json` をそのまま流し、ソルバーを Codex から**ローカルの
Qwen3.5-9B**（nonthinking / IQ4_XS / RTX 2060 6GB / 41.6 tok/s）に替えたものです。
題材・計画・ランナーは同一で、差分はソルバー1つ。

| | run 5（Codex） | run 6（ローカル 9B） |
|---|---|---|
| 無介入の緑 | 11/11 | **11/11** |
| ステップあたりの試行 | ほぼ1 | **1**（全ステップ 1 attempt） |
| エスカレーション | 1回（プランナーが自分で解決） | **0** |
| 実行時間 | 19分37秒 | **15分12秒** |
| 最終スイート | 48件パス・skip 0・回帰 0 | 同左 |
| 人間の介在 | **ゼロ** | **ゼロ** |

計画の作成は run 5 で15分02秒（自己修正が1回発動し、2回目で通過）。run 6 は同じ計画を
使うため計画の作成を行っていません。

**弱いソルバーでも結果が落ちなかったことが、この構成の主張そのものの検証になっています**
── 合格基準を外に置けば、それを満たす側の質は結果を支配しない。実装 268 行を目視で
確認し、テストを通すためのハードコードは1件もありませんでした。

これ以前にも 10ステップ緑を2回（run 1 / run 2）、コールドスタートをプランナーが自力で解いた run 3 があります。

## 適用範囲

**Python + pytest と、TypeScript + vitest を検証手段とする題材に対応します。** 題材そのものには依存していません（`loop.py` に題材固有の記述はありません）。言語ごとの違いは `loop.py` の `LANGUAGES` にまとめてあり、テストの起動と判定、赤の判定、契約の読み取り、スタブの組み立て、環境の事実の伝え方が言語を見て分岐します。

TypeScript では happy-dom が画面の無い DOM を作るので、ボタンを押して表示が変わることまでテストで確かめられます。

## 環境構築について

対象環境は Windows 上の WSL2 `Ubuntu-24.04` です。構築作業はホストや WSL の設定、SSH 鍵、ユーザー権限、ネットワーク制御を変更します。コマンドを抜粋して実行せず、先に [provision/README.md](provision/README.md) の前提、手順、既知の落とし穴を通して確認してください。

WSL2 は既定のままでは隔離環境ではありません。この構成では Windows ドライブの自動マウント、Windows 実行ファイルとの相互運用、WSLg を明示的に無効化し、プロビジョニング後に状態を検証します。普段使いのディストロとは別に、専用のディストロを作ってください。
